## §0 一页结论

| 问题 | 结论 |
|---|---|
| 要不要整体换掉前端图谱？ | **不要整体换。** 保留 ReactFlow 做"骨架编辑（TBox）"，**新增** Sigma 只读模式做"实例探索（ABox）" |
| 为什么不全换？ | 需求 4 要求"人工审核 + 调整修改 schema"，ReactFlow 的 Handle 连线/拖拽是 Sigma 没有的能力；且 `OntologyBuilderPage.tsx` 已 3,835 行，动它风险大 |
| 核心工作量在哪？ | **不在换渲染器，在写数据契约适配器**（§9）。Explorer 前端只消费 7 个节点字段 + 9 个边字段，平台只需把 `graph_data` 投影成这个形状 |
| 要不要移植 Explorer 的 Python 后端？ | **绝对不要。** `semantica/explorer/app.py` 自述 *"GraphSession uses an in-memory ContextGraph and does not open a network connection to FalkorDB"* —— 它是会话级内存图，不是多租户持久化后端。平台已有 Neo4j/Milvus，写一个投影适配器即可 |
| 最大的"不能照搬"点在哪？ | `graphEntityShape.ts` 的 4 条正则**全是生物医学词**（gene/protein/disease/drug/pathway），对中文本体完全失效 —— 所有节点都会 fallback 成同一种形状（§7） |
| 预期收益 | 渲染上限 **1~2k → 25k+ 节点**；布局可复现；中文标签不重叠；新增搜索/图例/邻域/聚类/时间轴 |
| 工作量 | **13 人日**（4 批），详见 §13 |

### 1.3 为什么"图谱展示不太行"——三个根因

**根因 ①：dagre 把网状本体拉成长链。**
`layoutUtils.ts:16-27` 用 dagre 的 `rankdir: 'LR'`。dagre 的定位是"有向无环图的分层布线"（流程图、依赖树）。本体是**带环的、多对多的、以类为枢纽的星型+网状混合结构**，喂给 dagre 的结果就是：一条横贯屏幕的主干链，两侧挂着稀疏的分支，视觉重心完全错位。

**根因 ②：孤立节点被扔到右下角，造成视觉断裂。**
`layoutUtils.ts:63-80`：

```ts
const cols = Math.max(1, Math.ceil(Math.sqrt(isolatedNodes.length)));
const gridStartX = maxX > 0 ? maxX + 150 : 100;   // ← 追加到已连图的最右侧
const gridStartY = 100;
const colSpacing = 280;
const rowSpacing = 160;
```

孤立节点（未参与任何关系的实例）被排到 `maxX + 150` 之外的一个独立网格里。用户的观感就是：**左边一团挤在一起，右边一片散落的点**，中间空一大片。这正是"展示不太行"最直观的来源。

**根因 ③：80px 圆 + 2 行截断，中文标签必溢出。**
`Neo4jNode.tsx:29-30`：Class 节点 `fontSize = 12`、`size = 80`。80px 直径的圆，`fontSize 12` 一行最多放 5 个汉字，`WebkitLineClamp: 2` 后第 6 个字起直接看不见。中文实体名普遍 4~8 字（"理财产品销售机构" = 8 字），**大部分标签是残缺的**。

### 1.4 结论

现有实现的问题**不是"代码写得差"，而是"选错了渲染范式"**：用 DOM 做图可视化，注定卡在 1~2k 节点；用 dagre 做本体布局，注定形变。这两件事都是**换技术栈才能解决**的，不是调参数能解决的。

## §3 关键设计一：LOD 三级缩放

Explorer 的核心体验来源：**按缩放比例切换信息密度**，而不是"永远渲染全部"。定义在 `graphTheme.ts:497-534`：

```ts
zoomTiers: {
  // 缩略：只看结构和轮廓
  overview: {
    maxRatio: Number.POSITIVE_INFINITY,
    nodeScale: 0.72,
    labelThreshold: 0.998,      // 只有前 0.2% 的节点显示标签
    labelBudget: 2,             // 全屏最多 2 个标签
    edgePriorityThreshold: 0.72, // 只画最重要的 28% 的边
    arrowPriorityThreshold: Number.POSITIVE_INFINITY, // 完全不画箭头
    edgeSizeScale: 0.62,
    showBadges: false,
    showCurves: true,
    showContextualArrows: false,
  },
  // 结构：看聚类与主干
  structure: {
    maxRatio: 1.2,
    nodeScale: 0.94,
    labelThreshold: 0.95,
    labelBudget: 12,
    edgePriorityThreshold: 0.4,
    arrowPriorityThreshold: 0.75,
    edgeSizeScale: 0.92,
    showBadges: false,
    showCurves: true,
    showContextualArrows: false,
  },
  // 检视：看细节与属性
  inspection: {
    maxRatio: 0.5,
    nodeScale: 1,
    labelThreshold: 0.8,
    labelBudget: 40,
    edgePriorityThreshold: 0,      // 画全部边
    arrowPriorityThreshold: 0.45,
    edgeSizeScale: 1.18,
    showBadges: true,              // 显示角标（属性数、告警）
    showCurves: true,
    showContextualArrows: true,    // 只给"当前关注节点"的边画箭头
  },
},
```

**关键机制说明**：

1. **`maxRatio` 是"该层级适用的最大相机比例"**，三层从上到下按 `maxRatio` 递减匹配 —— 实际是 `overview → structure → inspection` 的**放大过程**（`overview` 的 `Infinity` 兜底所有缩小状态）。
2. **`labelBudget` 是硬预算，不是阈值** —— 配合 `labelThreshold` 先筛出候选，再按 `labelPriority` 取前 N 个。这是"密图不糊"的根本原因：不是让标签变小，而是**根本不多画**。
3. **`edgePriorityThreshold` 让边也参与 LOD** —— 缩略时只画 28% 的边，视觉立刻清爽。
4. **`showContextualArrows` 而非全局箭头** —— 箭头只在 `inspection` 层且只针对当前 hover/选中的节点显示，避免"满屏箭头噪点"。

### 3.1 中文场景调整建议

| 参数 | Explorer 值 | 建议值 | 理由 |
|---|---|---|---|
| `overview.labelBudget` | 2 | **4** | 中文标签 2~4 字即可辨识（"合同"/"客户"），信息密度高于英文 |
| `structure.labelBudget` | 12 | **20** | 同上 |
| `inspection.labelBudget` | 40 | **60** | 检视层用户已明确要看细节 |
| `overview.labelThreshold` | 0.998 | **0.99** | 放宽候选池，让 `labelPriority` 有得挑 |

> 依据：中文单字信息密度约为英文单词的 2~3 倍，同等屏幕面积下可承载的标签数更多。

## §4 关键设计二：确定性小组件网格布局（解决"散点"）

这是**直接命中 §1.3 根因 ②** 的设计。Explorer 用 135 行（`smallGraphLayout.ts`）解决"小图 + 多个不连通分量 → 看起来像一把散落的点"：

```ts
export const SMALL_GRAPH_MAX_NODES = 48;
const PROVIDED_COORDINATE_COVERAGE = 0.92;   // 92% 节点已有坐标 → 直接用坐标
const MAX_COMPONENT_RADIUS = 78;             // 单个分量的最大半径
const COMPONENT_GAP = 48;                    // 分量之间的间隙
```

### 4.1 决策函数（三分支）

```ts
export function resolveGraphLayoutDecision(nodeCount: number, coordinateCoverage: number) {
  const useProvidedCoordinates = coordinateCoverage >= PROVIDED_COORDINATE_COVERAGE;
  const useSmallGraphLayout = shouldUseSmallGraphLayout(nodeCount, coordinateCoverage);
  return {
    useProvidedCoordinates,
    useSmallGraphLayout,
    layoutReady: useProvidedCoordinates || useSmallGraphLayout,
  };
}
```

| 场景 | `useProvidedCoordinates` | `useSmallGraphLayout` | 行为 |
|---|---|---|---|
| 节点 ≤ 48 且 坐标覆盖率 < 92% | false | **true** | 走确定性小组件网格（本设计核心） |
| 坐标覆盖率 ≥ 92% | **true** | false | 直接用后端给的 x/y（保存过的布局） |
| 节点 > 48 且 无坐标 | false | false | 交给 ForceAtlas2 跑力导向 |

### 4.2 算法（`buildSmallGraphSeedPositions`）

```
1. 节点按 id 字典序排序，建邻接表
2. BFS 求连通分量
3. 每个分量内部按"度数降序 → id 字典序"排序（枢纽节点排前面，环上位置更显眼）
4. 分量之间按"规模降序 → 首元素字典序"排序
5. 分量打包进居中网格：
     columns = ceil(sqrt(分量数))
     cellWidth  = 78 * 2 + 48 = 204
     cellHeight = 78 * 2 + 48 = 204
     centerX = (col - (columns - 1) / 2) * cellWidth     ← 居中，不是靠右
     centerY = (row - (rows - 1) / 2) * cellHeight
6. 分量内环形排布：
     radius = min(78, 30 + len * 9)      // 单节点分量直接落在格心
     angle  = -PI/2 + i * 2PI / len      // 从正上方开始顺时针
```

源码里有一句注释值得抄进平台：

> *"ForceAtlas2 is useful for large connected datasets, but it makes tiny graphs with several disconnected components look like scattered dots. This layout keeps each connected component together and packs components into a centered grid so instance relationships remain legible on first render."*

**对比现有实现**（`layoutUtils.ts:63-80`）：

| 维度 | 现有 | Explorer | 差异 |
|---|---|---|---|
| 孤立节点位置 | `maxX + 150`（右侧追加） | 居中网格 | 视觉重心居中 |
| 孤立节点排布 | 行列网格（`colSpacing 280`） | 环形（半径 ≤78） | 紧凑，不占大片空白 |
| 连通分量 | 完全不区分，统一进 dagre | 每个分量独立成环 | 语义分组清晰 |
| 确定性 | `Math.random()` 噪声 | 全字典序 | **可复现** |
| 单节点分量 | 与其他孤立节点同列 | 落在格心 | 整齐 |

### 4.3 中文场景调整

| 参数 | Explorer 值 | 建议值 | 理由 |
|---|---|---|---|
| `MAX_COMPONENT_RADIUS` | 78 | **96** | 中文标签 chip 更宽（§5），半径需留出标签空间 |
| `cellWidth/cellHeight` | 204 | **240** | 随半径同步放大（`96*2 + 48`） |
| `SMALL_GRAPH_MAX_NODES` | 48 | **48**（保持） | 48 个节点按 7 列网格已是屏幕上限 |

## §5 关键设计三：Canvas2D 标签 chip 与 hover 卡

`sigmaNativeRendering.ts`（421 行）是"图看起来专业"的关键。它不用 Sigma 默认的裸文本标签，而是自绘**圆角矩形标签片**：

```ts
// 自定义节点程序类：圆 + 描边 + 自绘标签
export const SEMANTICA_NODE_PROGRAM_CLASSES = {
  ...DEFAULT_NODE_PROGRAM_CLASSES,
  circle: EntityTokenNodeProgram,
};

// 自定义边程序类：真曲线 + 曲线箭头
export const SEMANTICA_EDGE_PROGRAM_CLASSES = {
  ...DEFAULT_EDGE_PROGRAM_CLASSES,
  curve: EdgeCurveProgram,
  curvedArrow: EdgeCurvedArrowProgram,
};
```

三个自绘函数：

| 函数 | 作用 | 关键实现 |
|---|---|---|
| `drawSemanticaNodeLabel` | 常驻标签片 | `ctx.measureText` 测宽 → `drawRoundedRect(ctx, x, y, w, h, chipTheme.radius)` → 阴影 + 文字 |
| `drawSemanticaNodeHover` | hover 双行卡 | 第一行 = 标签；第二行 = **大写 meta 标签**（如 `ENTITY · 12 PROPS`） |
| `drawRoundedRect` | 圆角矩形工具 | 手写 arcTo 路径（避免 `roundRect` 的浏览器兼容问题） |

### 5.1 中文适配（必做）

## §6 关键设计四：可见节点图例与语义着色

`graphColorLegend.ts` 只有 36 行，但有两个**容易踩坑的细节**：

```ts
export function buildGraphColorLegend(graph: Graph, theme: GraphTheme = GRAPH_THEME) {
  const entries = new Map<string, GraphColorLegendItem>();
  graph.forEachNode((_nodeId, attrs) => {
    if (attrs.hidden) return;                                   // ① 只看可见节点
    const group = String(attrs.semanticGroup || attrs.nodeType || "entity");
    // ② 用 semanticBaseColor 优先，避免交互态（hover/选中）颜色污染图例
    const color = String(attrs.semanticBaseColor || getSemanticNodeColor(attrs, theme));
    const id = JSON.stringify([group, color]);                  // ③ group+color 复合键
    const existing = entries.get(id);
    if (existing) existing.count += 1;
    else entries.set(id, { id, group, color, count: 1 });
  });
  return [...entries.values()].sort((a, b) => a.group.localeCompare(b.group) || a.color.localeCompare(b.color));
}
```

**三个细节的设计意图**：

1. **`if (attrs.hidden) return`** —— 图例必须跟随过滤结果。用户筛掉了"低置信度"节点，图例里就不该再出现对应的颜色项。
2. **`semanticBaseColor || ...`** —— 交互态（hover 时节点变亮）会临时改写 `color`，若不隔离，图例颜色会随鼠标乱跳。`semanticBaseColor` 是"语义色快照"。
3. **`JSON.stringify([group, color])`** —— 用复合键而非 `group` 单键。因为**同名的语义组可能被分配不同颜色**（合成节点、跨域同名类型），单键会丢项。

### 6.1 语义着色：自动选色字段（`useLoadGraph.ts:31-41`）

```ts

  "community", "cluster", "module", "group", "category",
  "domain", "layer", "source", "nodeType",
] as const;
```

`chooseColorAccessor()` 用**归一化信息熵**从这 9 个字段里挑"区分度最高"的一个作为着色依据：

取 entropy 最大的字段 → 该字段的取值决定节点颜色

**中文场景必须改这个字段表** —— 上面 9 个字段是 Semantica 的图模型，平台的字段名不同：

### 7.1 重写方案：按知识域配置的形状表

```ts
// src/features/graph-explorer/graphEntityShape.ts（平台版，全量重写）

  // 通用（对齐 owl:*）

  "owl:NamedIndividual": "individual",
  "owl:ObjectProperty": "property",

  "地点": "location", "地区": "location", "国家": "location", "地址": "location",
  "事件": "event", "事故": "event", "交易": "event", "会议": "event",
  "时间": "time", "日期": "time", "期限": "time", "时点": "time",
  "金额": "quantity", "数量": "quantity", "比例": "quantity", "利率": "quantity",
  "文档": "document", "合同": "document", "报告": "document", "制度": "document",
  "法规": "regulation", "监管规定": "regulation", "法律": "regulation", "条例": "regulation",
  "产品": "product", "理财产品": "product", "服务": "product",
  "概念": "concept", "术语": "concept", "指标": "concept", "分类": "concept",
};

/**
 * 兜底关键词（类型名不在表里时，用包含匹配）。
 */
export const ENTITY_SHAPE_KEYWORDS: Array<[GraphEntityShapeVariant, string[]]> = [
  ["person",       ["人", "员", "客户", "经理", "董事"]],
  ["organization", ["机构", "公司", "企业", "集团", "部门", "银行", "中心", "委员会"]],
  ["location",     ["地", "省", "市", "区", "国", "路", "街"]],
  ["event",        ["事件", "事故", "活动", "交易", "操作"]],
  ["time",         ["时间", "日期", "期限", "年度", "季度"]],
  ["quantity",     ["金额", "数量", "比例", "率", "额", "值"]],
  ["document",     ["文档", "文件", "合同", "报告", "协议", "通知"]],
  ["regulation",   ["法规", "规定", "办法", "条例", "准则", "指引"]],
  ["product",      ["产品", "服务", "业务", "方案"]],
  ["concept",      ["概念", "指标", "分类", "类别", "标准"]],
];

export function classifyEntityShape(
  nodeType?: string,
  semanticGroup?: string,
  content?: string,
  properties?: Record<string, unknown>,
): GraphEntityShapeVariant {
  // 1) 精确匹配：优先看结构化类型字段
  const typeCandidates = [
    nodeType,
    semanticGroup,
    String(properties?.entityType ?? ""),
    String(properties?.owlClass ?? ""),
    String(properties?.type ?? ""),
    String(properties?.category ?? ""),
  ].filter((v): v is string => typeof v === "string" && v.trim().length > 0);

  for (const candidate of typeCandidates) {
    const exact = ENTITY_TYPE_SHAPE_MAP[candidate.trim()];
    if (exact) return exact;
  }

  // 2) 关键词包含匹配：类型字段 + 标签文本一起扫
  const haystack = [...typeCandidates, content ?? ""].join(" ");
  for (const [shape, keywords] of ENTITY_SHAPE_KEYWORDS) {
    if (keywords.some((kw) => haystack.includes(kw))) return shape;
  }

  return "entity";
}
```

## §8 性能三级策略（8000 / 25000 阈值）

`graphConfig.ts:37-41` 定义了三道阈值：

```ts
thresholds: {
  interactiveLayoutMaxNodes: 8000,   // ≤8000：Worker 实时跑 FA2
  stagedLayoutMaxNodes: 25000,       // 8000~25000：分阶段布局 + 渐进渲染
  focusNeighborCap: 18,              // 邻域面板最多 18 个邻居
  focusPrimaryLabels: 8,             // 聚焦态最多 8 个主标签
  particleEdgeCap: 32,               // 粒子动效最多 32 条边
}
```

### 8.1 三档策略

| 档位 | 节点数 | 布局方式 | 渲染方式 | 交互 |
|---|---|---|---|---|
| **A 交互式** | ≤ 8,000 | ForceAtlas2 Web Worker 实时迭代 | 全量进 Sigma | 拖拽/缩放/搜索/邻域 全功能 |
| **B 分阶段** | 8,000 ~ 25,000 | 分阶段布局（先跑 N 轮收敛，再增量微调） | 渐进式渲染 + 加载进度条 | 缩放/搜索可用；拖拽禁用 |
| **C 服务端预布局** | > 25,000 | **服务端离线算好坐标** | 前端直读 x/y，不做任何布局 | 仅缩放 + 搜索 + 点击详情 |

### 8.2 档位 C 是平台必须补的能力

Explorer 是"会话内看图"，可以等前端慢慢跑 FA2。**平台不行** —— 用户点开一个 5 万节点的项目，不可能等 30 秒。

**平台侧实现**：

**逐参数意图**：

| 参数 | 作用 | 调错会怎样 |
|---|---|---|
| `barnesHutOptimize` | 斥力用四叉树近似 | 关掉 → 10k 节点卡死 |
| `barnesHutTheta: 0.6` | 近似精度 | 调大 → 更快但布局粗糙；调小 → 精确但慢 |
| `linLogMode: true` | 对数距离加权 | 关掉 → 所有节点均匀铺开，看不出社区 |
| `outboundAttractionDistribution` | 按出度分配引力 | 关掉 → 枢纽节点被甩到边缘 |
| `gravity: 0.14` | 向心力 | 调小 → 孤立分量飞走；调大 → 挤成一坨 |
| `scalingRatio: 4.8` | 整体斥力 | **中文场景建议 6.0**（长标签需要更多空间） |
| `slowDown: 6` | 阻尼 | 调小 → 抖动；调大 → 收敛慢 |

import base64, json

def encode_cursor(offset: int) -> str:
    return base64.urlsafe_b64encode(json.dumps({"o": offset}).encode()).decode()

def decode_cursor(cursor: str | None) -> int:
    if not cursor:
        return 0
    try:
        return int(json.loads(base64.urlsafe_b64decode(cursor).decode())["o"])
    except Exception:
        return 0

| `target` | → | `target` | |
| `data.label` | → | `type` | 中文关系名（"隶属于"/"发行"） |
| `data.weight` | → | `weight` | 缺省 1.0 |
| `data.properties` | → | `properties` | 透传 |
| `data._isBidirectional` | → | `properties.is_bidirectional` | 现在在 `OntologyCanvas.tsx:109-123` 前端算，**移到后端算**（更稳） |

### 9.4 为什么要"移到后端算双向边"

现有实现（`OntologyCanvas.tsx:109-123`）在前端统计同对节点出现次数来决定是否画双向偏移。问题：

1. 每次数据变化都要全量重算（O(E)）；
2. 分页加载时只能看到当前页，**判断错误**（第 1 页看不到第 2 页的反向边）；
3. 与后端真相不一致。

**改法**：后端在投影时，用一个 `Map<[min,max], count>` 一次扫完所有边，把 `is_bidirectional` 写进 `properties`。前端直接用。

### 9.5 关键决策：**不要移植 Explorer 的 Python 后端**

证据（`semantica/explorer/app.py:47-49` 原文注释）：

> *"These are read and stored for future use when direct FalkorDB connection support is added to the Explorer. Currently GraphSession uses an **in-memory ContextGraph** and does not open a network connection to FalkorDB."*

含义：

| 维度 | Explorer 后端 | 平台需要 |
|---|---|---|
| 数据源 | 进程内 `ContextGraph`（内存） | Neo4j + MySQL 持久化 |
| 多租户 | ❌ 无 `project_id` 概念 | ✅ 必须按项目隔离 |
| 权限 | 单一 API Key（`dependencies.py:require_auth`） | ✅ 需求 1 的模块/角色门禁 |
| 生命周期 | 进程重启即丢 | ✅ 持久 |
| 分页 | ✅ 有（`next_cursor`） | ✅ 复用形状 |

**结论：只借它的"前端渲染栈"和"线上契约形状"，后端完全自研。** 这也让工作量从"移植 20 个路由"降到"写 2 个只读端点"。

## §10 共存模型：双模式

### 10.1 模式划分

| 模式 | 技术 | 用途 | 可编辑 | 对应需求 |
|---|---|---|---|---|
| **骨架编辑（TBox）** | ReactFlow（**保留**） | schema 人工审核：拖拽类、连线、改属性、增删 | ✅ | 需求 4「必要时标记人工审核，由人判断」 |
| **实例探索（ABox）** | Sigma（**新增**） | 可视化查看、搜索、聚类、路径、时间轴 | ❌ 只读 + 可标注 | 需求 5「可视化查看和调整修改」 |

### 10.2 为什么必须保留 ReactFlow

1. **需求 4 要求"人工审核 + 调整修改"** —— 需要拖拽节点、拖 Handle 连线、右键删边。Sigma 是渲染库，**没有端口（Handle）概念、没有连线交互 UI**，做编辑要自己写一整套，成本远超收益。
2. **现有 `OntologyBuilderPage.tsx`（3,835 行）已经把 `extract-schema` → 人工编辑 → `extract-instances` 串起来了**。这个两阶段交互是平台**已经做对**的地方（`api/ontology.py:693` 注释："从项目 graph_data 中获取 schema（用户已审核的骨架）"），动它风险大、收益低。
3. **两种模式服务两种任务**：schema 阶段节点数少（几十个类），dagre/ReactFlow 完全够用；instance 阶段节点数多（几千~几万），才需要 Sigma。**不是替代关系，是分工。**

### 10.3 入口设计

`OntologyBuilderPage.tsx` 顶部加一个 Tab 组：

```
┌──────────────────────────────────────────────────────────┐
│  项目：XX银行知识图谱                                      │
│  [ 文档解析 ]  [ 骨架编辑 ]  [ 实例探索 ]  [ 时间轴 ]      │
│                  ↑ReactFlow   ↑Sigma(新)    ↑Sigma(新)   │
└──────────────────────────────────────────────────────────┘
```

路由：

```
/projects/:id/documents     文档解析
/projects/:id/schema        骨架编辑（现有 ReactFlow）
/projects/:id/graph         实例探索（新 Sigma）
/projects/:id/timeline      时间轴（新，Sigma + vis-timeline）
```

### 10.4 双向联动（P2，可选）

| 动作 | 效果 |
|---|---|
| 在「骨架编辑」选中 `owl:Class: 理财产品` → 点「在实例探索中查看」 | 跳转 `/projects/:id/graph?focusClass=<uri>`，Sigma 自动高亮该类的全部实例 + 相机聚焦 |
| 在「实例探索」点节点 → 点「查看所属类」 | 跳回 `/projects/:id/schema?highlight=<classUri>` |

实现：URL query 参数 + 两边各读一次 `useSearchParams`。成本很低，体验提升明显。

### 11.4 配色：深色 vs 浅色

Explorer 的 `GRAPH_THEME`（`graphConfig.ts:1-35`）是**深色太空风**：

```ts
background: { canvas: "#050816", shell: "#0A1021", panel: "#10182C" }
nodes: { palette: ["#3CE7FF","#23D7C8","#5DA9FF","#9B6BFF","#FF4FD8","#FF9A3C","#B9FF3B"], selected: "#FFC857" }
edges: { baseColor: "rgba(126,162,214,0.08)" }
```

平台现状是**浅色**（`OntologyCanvas.tsx:392` `bg-[#f8f9fa]`，`layoutUtils` 配色 `#4a90d9` 蓝 / `#f79767` 橙 / `#c990c0` 紫）。

**两个选项**：

| 选项 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| A（推荐） | 图谱页**单独用深色主题**（与平台其它页浅色并存） | 直接用 Explorer 全套配色，零调色成本；深色背景对 WebGL 图的视觉对比最有利 | 需要图谱页有独立的主题作用域 |
| B | 把 `GRAPH_THEME` 改成浅色版 | 与平台视觉统一 | 需要重调 7 色 palette 的对比度，`edges.baseColor` 的 `0.08` 透明度在浅色下几乎不可见，必须重算 |

选 A 时，给图谱页容器加 `data-theme="graph-dark"`，`GRAPH_THEME` 原样使用。
