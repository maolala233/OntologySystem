# 15 - 本体平台可信化优化方案

> 2026-10-25 起草。综合三个参考实现的分析结论（NVIDIA auto-ontology、AWS context-ontology-accelerator、人大 EvoOntology），给 OntologySystem 一套完整的可信化优化路线。
> 定位约束：**本体构建平台——构建本体、对外提供服务、让智能体运行时更准确可信**。
> 参考实现保留在 `test/auto-ontology`、`test/context-ontology-accelerator`、`test/EvoOntology`，按需回查。

## 0. 设计框架：三环可信 + 一个地基

| 环节 | 含义 | 现状 | 主要参考 |
|---|---|---|---|
| **构建可信** | 抽出来的本体本身是对的、可溯源的 | 抽取双通道+白名单+SHACL 门禁+人审（强） | AWS COA、EvoOntology |
| **运行时可信** | Agent 用本体时拿到的语义可靠、可拒绝、可溯源 | MCP 网关有 tokens/限速，但工具面是"查图"不是"给语义" | EvoOntology、NVIDIA |
| **进化可信** | 本体随使用变好，且**永远不会被改坏** | evolution_service 有雏形，无门禁无评估 | EvoOntology |
| **治理地基** | provenance / 认证位 / 版本原语 | provenance.py 雏形；versions/publications 已有 | 三家共有 |

四条原则（贯穿所有阶段）：

1. **机器产物默认不可信**：一切抽取/LLM 产物进库即 `certified=false`，人审置真，且重跑永不覆盖人工内容。
2. **确定性核心管门禁**：LLM/copilot 只能"提议"，accept/reject 由代码从持久化输入**重算**，不能被模型说服。
3. **语义服务可拒绝**：给 Agent 的每个语义断言带 coverage_status 和证据；不确定就返回 uncertain/ambiguous，不给编造的机会。
4. **进化必须配对证明**：候选版本发布前必须复现地优于父版本，否则保留父版本。

## 2. 阶段详设

### S16 语义资产地基（provenance 四态 + certified 位 + Evidence 一等公民）

**目标**：让"这条知识是谁说的、有没有人背书、凭什么"成为数据模型的一部分，并保证重跑/自进化永不冲掉人工成果。这是后续所有阶段的地基。

**改动点**：

1. `app/adapters/provenance.py` 升格为枚举合同：
   - `source_type ∈ {deterministic, ai, steward_edited, steward_specified}`（对齐 COA 的 EnrichmentSource）；
   - `certified: bool`（人工认证位，NVIDIA 式布尔位；只有审核动作能置真）；
   - 落库规则：抽取/LLM 通道写入 → `ai`；规则通道 → `deterministic`；人工编辑已存在对象 → `steward_edited`；人工新建/覆写关键判定字段 → `steward_specified`。**steward_edited/specified 一经写入，任何自动流程不得改写。**
2. 新增 `Evidence` 实体（表 + 模型 + CRUD）：
   - 字段对齐 EvoOntology：`{id, project_id, source_kind(document_page|ocr_block|table_probe|db_query|manual), source_ref(文档id/页码/块id), query, result, validation_method, created_at}`；
   - S14 解析产物（原文段落/页码/OCR 块）天然映射为 Evidence——解析完成即批量建 Evidence 行；
   - 类/关系/实例/公理四类资产增加 `evidence_refs: JSON` 列。
3. `merger.py` 合并保护（NVIDIA `merge_column_attribute` 语义）：合并只补不抹——目标字段已 `certified=true` 或 `source_type ∈ {steward_*}` 时，机器新值只能进"建议"侧（`suggestion` 字段，UI 提示待采纳），不得直接覆写。
4. `review_service.py`：审核通过动作 = 置 `certified=true` + 记 provenance 变更 + 审计日志；审核面板（前端）展示证据引用并支持一键认证。
5. 引用完整性校验器（EvoOntology `validate.py` 的移植）：`evidence_refs` 悬空 → 校验失败。先做成独立函数，S18 挂进发布门禁。
6. 存量迁移：全部存量资产 `source_type=ai, certified=false`；提供一次性盘点脚本（temp/），发布门禁对存量项目发一次性豁免标记（grandfather），避免老项目被新门禁卡死。

**验收**：抽取重跑后，已认证资产内容不变、机器新值出现在建议区；悬空证据引用被校验器报出；249 个 pytest 回归全绿 + 新增合并保护单测。

### S17 版本与发布原语（候选/active 分离 + 幂等发布 + 事件驱动刷新）

**目标**：把"版本"变成可以安全做实验的对象——候选版本永不触碰线上指针，发布动作幂等，发布成功后下游自动收敛。

**改动点**：

1. `versions.py` / 数据模型：版本行增加 `is_candidate: bool`、`parent_version_id`、`status ∈ {draft, candidate, published, rejected}`；候选版本命名 `vN-cK`。**active 指针只能指向 published**，翻转即一行更新（EvoOntology `active.json` 语义）。
2. `publications.py` 发布三原语（对齐 EvoOntology store）：
   - `promote`（复制+激活）、`publish`（**不覆盖**：同内容重试安全，异内容报错——字节级比对）、`set_active`；全部原子写。
3. 发布成功 → 发内部事件（进程内事件表或 celery 任务即可，不引消息中间件）：**幂等**触发下游刷新——Milvus channel 重建、oxigraph sink 重灌、图缓存失效（COA `ontology.published` 模式，"重放收敛而不腐化"：每个下游刷新任务带版本号做幂等键）。
4. TTL 快照导出/导入复用现有 `ontology_imports`：候选版本可导出为 TTL，也可导入为**沙盒项目**（S22 评估的基础设施）。

**验收**：重复调用 publish 不产生重复副作用；候选版本在任何接口都不可被 QA/MCP 命中（只能显式按版本读）；发布后 Milvus/oxigraph 自动刷新且重复发布不重复重建。

### S18 三级质量门禁进发布流程

**目标**：发布前机检三道闸——逻辑一致性（Tier1 阻断）、结构成熟度（Tier2 打分）、外部踩坑扫描（Tier3 默认关），发布报告同时给出结果。

**改动点**：

1. **Tier1 阻断级**（`gate_service.py`，全部纯 Python，不引 Java）：
   - 分类环检测（`rdfs:subClassOf` 成环，图遍历）；
   - 不一致检测：在 owlrl 推理后的图上查 **disjointWith 冲突实例**（同一实例被推入两个互斥类）、domain/range 违例——owlrl 已在用（326 蕴含实测），补的是"把蕴含结果拿来做一致性判定"；
   - pySHACL 已有，保留；S16 的证据引用完整性挂入；
   - （可选增强）装 Java 时接 owlready2+HermiT 查不可满足类；注意 owlready2 的 HermiT 需要先在临时副本上替换不支持的 XSD 类型（`xsd:date→xsd:dateTime` 等），原库不动；owlready2 为 LGPL 依赖，只运行时使用不分发，合规无忧。**默认关闭，环境探测到 Java 才展示开关。**
2. **Tier2 打分级**（`scorecard_service.py` 新增"本体成熟度"区块，OntoQA 指标）：
   - 关系丰富度 RR = 对象属性数 / (对象属性+数据属性数)，**RR < 0.1 警告"本体基本只是分类树"**；
   - 属性丰富度 AR、分类最大深度（BFS）、孤立类计数、平均出度；
   - 不阻断，进 scorecard 前端区块 + 发布报告。
3. **Tier3 提示级**：OOPS 外部踩坑扫描，**默认关闭**（数据不出域——与安全底座叙事一致，COA 同款 opt-in 设计），设置页开关 + 明示数据外发提示。
4. 发布报告（reports）整合三级结果：Tier1 任一失败 → 阻断发布；Tier2 出分；Tier3 可选。
5. 受控关系枚举 prompt 契约：抽取白名单 prompt 中补 EvoOntology 的 5 关系决策优先级 + 常见错误表（禁 affects/belongs_to 自由文本），并在 `gate_service` 加关系类型白名单机检兜底。

**验收**：构造含分类环/disjoint 冲突的 TTL 被阻断发布；RR/深度在 scorecard 正确显示；249 回归绿。

### S19 MCP 语义服务面升级（运行时可信的核心）

**目标**：从"图数据库查询代理"升级为"语义服务"——Agent 会话初始化拿摘要，运行时按需取语义，每条断言带约束、严重级、证据和诚实信号。

**改动点**（`mcp_gateway.py`，保持现有工具与 tokens 完全向后兼容）：

1. **新资源 `ontology://manifest`**（会话初始化注入）：`{version, counts(类/实例/公理/规则), constraint_severity_histogram(block/warn/info), tools 清单, 使用指引("resolved 语义是引导不是最终答案，执行前须按约束校验")}`。只给摘要，不给全量——上下文成本恒定。
2. **新工具 `resolve_semantics(mentions[≤5], context?)`**：
   - 匹配层级：精确 id → 精确名 → 别名/同义词 → 词元子集；矛盾词过滤（问"月度"不返回"周度"概念）；
   - 每个提及返回 `coverage_status ∈ {supported, partial, unavailable}`；**消歧失败返回 `status=ambiguous` + 候选列表，绝不猜**；
   - 命中对象返回：Term/实体定义 + scope + **适用公理/约束（severity 排序，block 优先）** + 证据引用（S16 的 Evidence 内联展开）；
   - 硬上限：mentions ≤ 5、单工具响应 token 预算、**禁全量枚举**（空查询返回 `needs_query`）。
3. **新工具 `check_answerable(question)`**：实体识别 → Milvus+图覆盖率打分 → `{answerable: full|partial|no, uncovered: [...]}`。给 Agent 的元工具：先问能不能答，再花成本提问。
4. 工具 schema 用 Literal 枚举防 LLM 编造参数值；工具描述写明"读语义不执行业务"；写路径维持现状（tokens + WRITE_TOOLS + 审批）。
5. `docs/` 补 MCP 使用说明（含推荐调用序列：read manifest → resolve → check_answerable → 执行）。

**验收**：Claude Code/Cursor 经 MCP 连入：manifest 可读；"跨境汇款"解析回带 block 级约束与证据的完整语义包；问一个本体没覆盖的概念返回 `unavailable` 而非编造；现有 5 个旧工具回归通过。

### S20 QA 分层编排 + 历史合格性

**目标**：确定性优先，LLM 兜底；覆盖不足不硬答；多轮上下文干净。

**改动点**（`qa.py`）：

1. **Tier0 确定性匹配**（COA Tier1 指标解析模式）：术语别名/实例名/（S24 后）指标名的同义词词典精确命中 → 直接走权威上下文路径（返回该概念的口径/约束）；**部分命中时不升级也不硬答，把命中概念的权威口径作为上下文转发给下一层**（COA"残余限定词转发"）。当前 Milvus+IDF+图融合链路降级为 Tier1/2。
2. **答案性预检**：复用 S19 的覆盖率打分（内部调用，不走 MCP），覆盖不足（`no`）→ 直接转 copilot 澄清（已有"至少 3 选项"机制）；`partial` → 答案中明示未覆盖部分。
3. **对话历史合格性过滤**（NVIDIA 规则）：只保留最近 5 轮、总量 12k 字符、且"合格"的轮次（失败回答/图表/原始行不入上下文）；追问改写用轻量模型判定 `is_follow_up`，**判定为独立问题时代码强制原样返回，不信模型**（本地合同强制）。
4. SSE/前端不变（内部改造）。

**验收**：精确命中指标口径的问题不再走向量检索（可测延迟与稳定性）；40 题 QA 分数不降（回归门禁）；否定题 5/5 保持。

### S21 轨迹与进化触发器

**目标**：把 Agent 交互变成可信的进化素材——只记可观察行为，拒伪造，攒够素材自动提醒进化。

**改动点**：

1. 新增 `trajectory` 模块（表 + service）：
   - 结构对齐 EvoOntology：`{task_id, question, ontology_version, split, semantic_calls[{tool,input,result}], tool_calls[{tool,input,result(截断 2000 字/20 行),result_summary}], final_answer, task_status(completed|failed|interrupted), errors, recorded_at}`；
   - **不记思维链**；QA 与 copilot 执行链路落点（copilot 工具步骤上屏 S15 已有数据源）；
   - 事件幂等（event_id 去重重试）；**completed 任务必须至少一条真实工具观察**，否则拒收（反伪造合同）。
2. 触发器（`trigger` 状态表 + evolution API 端点）：自 checkpoint 起新增轨迹 **≥30 条或 ≥7 天**（均可配）→ `evolution_due=true`；前端进化页横幅 + copilot 可提示"该进化了"。**checkpoint 只在 S22 门禁通过后推进**。
3. 轨迹查询 API（按时间窗、按状态过滤）供 S22 诊断用。

**验收**：走查一轮 QA+copilot 后轨迹表有合规记录；伪造的空观察被拒；阈值到达后横幅出现。

### S22 配对评估门禁（进化闭环核心，本方案灵魂）

**目标**：候选本体发布前必须配对证明"复现优于父版本"；accept 由确定性代码重算，进化系统不会被自己的 LLM 说服。

**改动点**（`evolution_service.py` 重构 + 新评估模块）：

1. **进化状态机**（对齐 EvoOntology `EvolutionSession`）：
   ```
   running --reject--> running（记录 rounds，不推进 checkpoint）
   running --accept--> accepted（发布 vN+1，推进 checkpoint）
   running --预算/中断--> incomplete（不发布不推进）
   ```
   - 冻结预算（默认 max_rounds=8，只能延长不能缩短）；反停滞规则：`incomplete(missing_data/unreliable_evaluation/external_block)` 需已积累 ≥2 次 reject 才允许；
   - 全程状态落库（run/rounds/evaluations 三表），可恢复（resume 拒绝重开终态 run）。
2. **候选产生**：诊断（人工+后续 S25 半自动）→ 一个候选一个主假设 → 候选版本走 S17 原语（`vN-cK`，不碰 active）。
3. **配对评估 harness**：
   - 评估集：**O4 的 40 题 QA 为固定验证集**（fixed_split 模式：40 题全部作为 validation reserve，不得用于诊断调参；生产轨迹负责诊断侧）；
   - 同 harness 同配置：同模型（显式 model_config_id，注意 glm-flash 单调用 5-10 分钟，批跑预算要留）、同温度、同检索配置，**唯一差异是本体版本**；
   - 沙盒：候选 TTL 导出 → `ontology_imports` 导入沙盒项目 → QA 指定沙盒 project_id 跑分（复用现有导入链路，零新基建）；
   - 产出逐题配对分数 + 每题回归标记，落 `eval_runs.gate_input`（含 `unacceptable_regressions` 显式布尔，评估者必须逐项核查后声明）。
4. **确定性门禁重算**（`gate_service` 或 evolution 内）：
   - GT 协议（40 题有标准答案）：`accept ⇔ candidate_avg > parent_avg`（严格大于）**且** `unacceptable_regressions == false`（显式声明，缺声明直接拒）；
   - 否定题单列：候选在否定题上的分数不得下降（防"多答"式进化）；
   - 无 GT 的场景（后续扩展）：LLM judge 协议——A/B 匿名化（随机标签）、judge 用独立 model_config、`accept ⇔ candidate 零 critical error 且胜场 > parent`（平局不计）；
   - **Agent/前端只能提交 gate_input，accept 与否由代码重算**；评估报告记录 `gate_input` 快照防篡改。
   - 显著性：40 题样本小，程序性纪律优先（小差距自动要求复跑确认）；`gate_input` 已带逐题配对数组，后续可加 bootstrap/配对检验（扩展点，本期不做数学检验）。
5. **reject 纪律**：拒绝轮记录 `{round, hypothesis, candidate, metrics, notes}`；checkpoint 不动，同一批轨迹可再来；前端进化页展示状态机 + 历史轮次 + 评估对比。
6. accept → S17 发布原语 + 事件刷新 + checkpoint 推进，一气呵成。

**验收**：构造一个变差的候选（删一条公理）→ 门禁拒绝且 checkpoint 不动；构造一个变好的候选（新增公理使否定题与综合题提分）→ 门禁通过、发布 vN+1、下游自动刷新；全程无人工点"通过"按钮的空间（只有"提交评估"）。

---

### S23 数据级授权（安全底座差异化，答辩强弹药）

**目标**：把权限从"能不能进系统"下沉到"能查到哪些语义"，fail-closed。

**改动点**：

1. `roles.py` 角色增加数据级授权字段（新 grant 表）：`domain_allowlist`（知识域白名单，复用现有 domains）、`class_denylist`、`property_denylist`；
2. 执行点（两处，都 fail-closed——授权数据缺失=拒绝而非放行）：
   - QA 检索：Milvus 过滤表达式 + 图查询过滤按角色裁剪；
   - MCP 工具：resolve/search 返回前按调用者角色裁剪（COA 模式：**用委托人身份鉴权，Agent 身份只进审计**）；
3. 审计日志记录每次裁剪；前端角色管理页加清单编辑（多选+搜索，符合既有交互偏好）。
4. 演示脚本：柜员角色问反洗钱域问题 → 明确"无权限"回答（不是编造、不是空结果），合规角色同问题完整回答+溯源。

**验收**：两角色对照走查；越权路径（直接 MCP 查询）同样被裁剪；fail-closed 测试（清空授权后默认全拒）。

---

### S24 GovernedMetric 指标层（差异化能力，可选但推荐）

**目标**：指标（支付成功率、退票率、单笔限额）成为本体一等公民，口径唯一权威来源；"本体不只管概念，还管指标口径"。

**改动点**：

1. 数据模型：指标作为特殊类节点 `subClassOf :GovernedMetric`（TTL 落地），属性：`口径表达式`（SPARQL ASK/SELECT 或结构化描述）、`单位`、`关联业务类`、`适用域`、severity；
2. 抽取接入：白名单模式加 `metric` 类型（对公支付文档里的"XX 率/限额/费率"高频出现）；LLM 通道 prompt 加指标抽取契约；
3. 校验（COA 6 项校验适配版，进 S18 门禁）：表达式可解析、引用的类/属性存在、单位必填、本体关联完整、（可执行时）空跑通过；
4. QA Tier0 接入（S20）：指标同义词精确命中 → 返回口径+关联约束，不走向量；
5. MCP `resolve_semantics` 自然覆盖（指标是 Term 的一种）；前端：类详情页/SchemaTab 支持指标类型展示。

**验收**：从制度文档抽出"大额支付审批限额"等指标并入库；问"单笔限额多少"直出口径+证据；指标口径修改走 S22 门禁。

### S25 Learn 闭环与收尾

**目标**：用量数据反哺本体；统一修复预算；打包 Agent Skills 用于答辩演示。

**改动点**：

1. **用量分析页**（前端新页 + 后端聚合 API）：QA 量/答率/澄清率/覆盖率分布/拦截次数（S23）趋势；NVIDIA `conversation_analytics` 模式，管理角色可见。
2. **未命中挖掘**：聚类 `unavailable/uncovered` 的提问 → 生成"缺失术语/关系/公理"建议 → 进审核队列（axiom_suggestion 通道复用）——进化候选的新来源。
3. **修复预算统一**（NVIDIA 门禁循环模式）：`tool_loop.py` / `extraction_repair.py` / copilot 执行器统一常量——重构 ≤7 次、软检查失败 5 次后放行不再阻断、全流程重启 ≤2 次且重启时恢复"不可变请求边界"（原始请求快照）、最后确定性兜底；杜绝无限循环与半途而废两个极端。
4. **Agent Skills 打包**（`skills/` 目录，答辩现场用 Claude Code 驱动系统）：三个 SKILL.md——
   - `ontology-setup`：连接 MCP、readiness 自检；
   - `ontology-management`：构建-审核-发布-进化全流程（写操作走 API 审批，MCP 只读）；
   - `ontology-query`：推荐调用序列 + "带断言答案核查清单"（总体/口径/单位/截断/证据，观察-计算-预测区分表述，fail closed）；
   - 结构抄 NVIDIA/COA：frontmatter + Overview + Quick Start + API 配方表 + **Common errors（症状/原因/修法）**。

**验收**：分析页出数；3 条建议进审核队列；技能驱动 Claude Code 完整走一遍"连接→查语义→问答"。

## 3. 并行工程实践清单（随阶段顺手做）

- **CI 契约漂移**：FastAPI openapi.json 提交入库 + CI diff 检查（NVIDIA 模式）；`alembic check` 查 schema 漂移。
- **黄金测试**：`merger.py` 固定夹具——"重跑抽取 over 已认证库 → 断言认证字段零变化"（S16 的守护测试）。
- **引用完整性测试**：全库无悬空 evidence_refs（S16/S18 共用）。
- **失败模式就地文档化**（COA 风格）：非显然约束写在代码现场（如"HermiT 需先替换 XSD 类型，否则整个推理 run 中止"）。
- **抽取提交确定性**：多通道合并按规范顺序串行提交（NVIDIA `_OrderedCommitQueue`），防并发命名碰撞。
- **pytest 基线**：249 全绿是每个阶段的回归底线；每阶段新增单测随阶段交付。

## 4. 实施顺序与里程碑

```
第 1 周   S16 地基 → S17 版本原语 → S18 质量门禁        【构建可信闭环】
第 2 周   S19 MCP 语义面 → S20 QA 分层                  【运行时可信闭环】
第 3 周   S21 轨迹触发 → S22 配对门禁                   【进化可信闭环】
第 4 周   S23 授权 + S25 收尾（S24 视档期）             【差异化与演示】
```

- **比赛最小叙事集**：S16+S19+S22+S18+S23 ≈ 1.5-2 周，支撑完整话术："构建可溯源（S16/S18）→ 运行时可拒绝可溯源（S19）→ 进化有门禁不会改坏（S22）→ 语义层权限到数据级（S23）"。
- 每阶段交付物 = 代码 + 单测 + 一次 IAB 走查 + 阶段小结（沿用既有习惯）。

## 5. 风险与对策

| 风险 | 对策 |
|---|---|
| HermiT/owlready2 需要 Java，部署环境未必有 | Tier1 主方案纯 Python（owlrl 蕴含图上做 disjoint 冲突/环/domain-range 检查）；HermiT 作可选增强，环境探测 Java 才开 |
| glm-flash 单调用 5-10 分钟，40 题配对评估耗时长 | 评估跑批脚本 + 显式 model_config_id；小差距复跑时只跑 40 题全集一次、复核跑抽样子集；评估在后台任务跑（celery） |
| 沙盒项目污染生产库 | 沙盒项目命名空间隔离（`eval_` 前缀 + project 标记位），评估完自动归档 |
| Milvus/oxigraph 重复重建 | 幂等键=版本号（S17）；刷新任务可重放 |
| 存量数据被新门禁卡死 | grandfather 豁免 + 一次性盘点脚本（S16） |
| 新 MCP 工具破坏现有调用方 | 工具只增不改；现有 5 工具回归测试；tokens 机制不动 |
| 轨迹记录侵入 QA/copilot 主链路 | 异步落库 + 落库失败不阻断主流程（打点降级） |

## 6. 明确不做

- NL2SQL 全家桶（多方言连接器、Ontop VKG、Athena federation）——与文档驱动定位不符；
- Smithy 契约优先多端代码生成——OpenAPI 够用；
- Cedar 及 AWS 侧实现——只借"forbid 压倒 permit""fail-closed""数据级授权挂角色"三个概念；
- COA"accept 只增不删"——反模式，图编辑+审计链路保留；
- 统计显著性检验的数学化（bootstrap/配对检验）——列扩展点，先程序性纪律。
