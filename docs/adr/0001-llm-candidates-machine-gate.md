# 公理建议采用 LLM 候选生成 + 确定性机检守门，而非规则挖掘

## Status

accepted

## Context

公理抽取需要从"统计推断三类公理"扩展。业界主流路线有二：一是关联规则挖掘（AnyBURL/AMIE，从实例图谱挖多跳 Horn 规则），二是 LLM 生成候选 + 确定性机检（SHACL/一致性校验）守门。

## Decision

采用第二条路线：LLM 通道与既有统计通道并行（双通道），LLM 产出的公理建议必须先过机检守门（存在性校验、公理冲突检测、影子校验）才能进入人工审核队列。

## Considered Options

- **规则挖掘优先**：被否。企业网银风控场景实例密度不足以支撑多跳规则的可信度（数千条关系起步），且 AnyBURL 为 Java 工具，进程集成成本高。留作实例积累后的二期选项。
- **LLM 候选直接进审核队列（不做机检守门）**：被否。LLM 生成约束类公理的幻觉率与误报率较高（幻觉类名、乱荐 disjoint），公理是强约束，错一条污染全部推理结果，机检守门不可省。

## Consequences

- LLM 是"候选生成器"而非"决策者"：其输出的类名/谓词必须能对回画布本体，对不上的直接拒。
- 影子校验复用 pyshacl，每次扫描增加约秒级校验成本。
- 若未来走规则挖掘，挖出的 Horn 规则转 SWRL 时需另行解决 SWRL 序列化导出问题。
