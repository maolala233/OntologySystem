## 一、🔴 P0 正确性缺陷

### 缺陷 1：实例前缀去重会误合并不同实体

**位置**：`extractor.py:2063-2078`，`merge_instances_to_graph_data()` 内

```python
def get_instance_prefix(label: str) -> str:
    """提取实例 label 的前缀（去除版本号等后缀）"""
    prefix = re.sub(r'[\s_]?[vV]?[\d\.]+$', '', label.strip())   # ← 元凶
    return prefix.strip()

# 按 (前缀, 类型) 分组，每组只保留属性最丰富的一个，其余合并进去
inst_groups: Dict[Tuple[str, str], List[dict]] = defaultdict(list)
for inst in instances:
    prefix = get_instance_prefix(inst["label"])
    inst_groups[(prefix, inst.get("type", ""))].append(inst)
```

**实测复现**（本机跑过）：

| 原始 label | 归一化后 | 后果 |
|---|---|---|
| `合同2024` | `合同` | 与 `合同2025` 合并成**一个实例** |
| `债券01` | `债券` | 与 `债券02` 合并 |
| `附件A1` | `附件A` | 与 `附件A2` 合并 |
| `A公司2` | `A公司` | 与 `A公司` 合并 |
| `理财产品3.0` | `理财产品` | 与 `理财产品` 合并 |

这类「同一前缀 + 尾部数字」的 label 在中文业务文档里**极常见**（合同编号、期次、附件序号、分公司序号）。这不是"合并重复"，是**把不同实体揉成一个**，且不可逆。

**设计意图的误解**：注释说"LLM 可能在多个 chunk 中提取出同一实体的不同版本（如量子安全平台 1.0、量子安全平台 2.0）"——但 `1.0` 和 `2.0` 本来就是**两个不同的东西**。真正需要合并的是「同一实体的不同**表述**」（全称/简称/别名），不是不同版本号。

**修法**：删掉前缀合并，改为三层收敛

```python
# 1) 只按确定性 id 精确合并（extract_instances 已经做了，这里不该再做一次）
# 2) 补一个保守的 label 归一（绝对不动数字）
def normalize_label_for_merge(label: str) -> str:
    s = unicodedata.normalize("NFKC", label or "").strip().lower()
    s = re.sub(r"\s+", "", s)                      # 去所有空白
    for suf in ("股份有限公司", "有限责任公司", "有限公司", "公司"):
        if s.endswith(suf) and len(s) > len(suf) + 1:
            s = s[: -len(suf)]
            break
    return s

# 3) 归一后仍不同 → 不合并，交给实体消解模块处理（见缺陷 10）
```

### 缺陷 2：整个 dict 塞进 prompt，换行变字面量

**位置**：`extractor.py:883-895`（`extract_schema`）、`:3064-3067`（`async_extract_schema`）

`_chunk_text()` 返回的是 `List[Dict]`（`{"text", "filename", "chunk_index"}`），但 schema 阶段直接把整个 dict 交给 `.format()`：

```python
chunks = self._chunk_text(text, chunk_size=chunk_size, overlap=chunk_overlap)  # List[Dict]
...
for i, chunk in enumerate(chunks):
    user_prompt = user_prompt_template.format(chunk=chunk)      # ← chunk 是 dict
```

**实测复现**：

```
实际发给 LLM：
【当前文本片段】:
"{'text': '第一行内容\n第二行内容，含"引号"。', 'filename': 'unknown', 'chunk_index': 3}"

正确做法：
【当前文本片段】:
"第一行内容
第二行内容，含"引号"。"
```

**三重损害**：

1. **`\n` 变成字面量反斜杠+n** —— LLM 看到的是两个字符，不是换行。文档的章节、条款、表格、列表结构**全部丢失**。中文文档里结构本身承载语义（"第X条"、"附则"、表格行列对应），这一项直接拉低骨架质量。
2. `'filename': 'unknown'` 污染 prompt，且**溯源信息在这里就断了**（`extract_schema` 没传 `filename`，全部是 `unknown`）。
3. `'chunk_index': N` 是无意义噪声。

**注意**：`extract_instances`（`:1423-1437`）**处理是对的**：

```python
if isinstance(chunk, dict):
    chunk_text = chunk.get("text", "")
    chunk_filename = chunk.get("filename", "unknown")
    ...
    user_prompt = f"""【文档来源】: {chunk_filename}\n""" + user_prompt_template.format(chunk=chunk_text)
```

所以同一个系统，**阶段 A 的 prompt 质量比阶段 B 差**，这是不一致而非设计。

**修法**：

```python
# extract_schema 增加 documents 参数（对齐 extract_instances）
def extract_schema(self, text=None, *, documents=None, ...):
    if documents:
        chunks = self._chunk_documents(documents, chunk_size=chunk_size, overlap=chunk_overlap)
    else:
        chunks = self._chunk_text(text, chunk_size=chunk_size, overlap=chunk_overlap,
                                  filename=filename)     # ← 补上 filename

    for i, chunk in enumerate(chunks):
        if isinstance(chunk, dict):
            chunk_text = chunk.get("text", "")
            chunk_filename = chunk.get("filename", "unknown")
        else:
            chunk_text, chunk_filename = chunk, "unknown"

        head = f"【文档来源】: {chunk_filename}\n" if chunk_filename != "unknown" else ""
        user_prompt = head + user_prompt_template.format(chunk=chunk_text)
```

### 缺陷 3：metadata 里的成功率是假的

**位置**：`extractor.py:1104-1112`

```python
"metadata": {
    "total_chunks": total_chunks,
    "successful_chunks": sum(1 for i in range(total_chunks)),   # ← 恒等于 total_chunks
    "failed_chunks": 0,                                         # ← 硬编码
    "success_rate": 1.0,                                        # ← 硬编码
    ...
}
```

`sum(1 for i in range(total_chunks))` 就是 `total_chunks`。**无论多少个分块失败，报告永远显示 100% 成功。**

后果：用户看到"抽取完成 24 个对象类型"，实际可能一半分块超时被静默跳过（`:897-903` 只 log warning 然后 `continue`）。

**修法**：

```python
successful_chunks = 0
failed_chunks: List[dict] = []

for i, chunk in enumerate(chunks):
    data = self._call_llm(...)
    if not data:
        failed_chunks.append({"index": i, "reason": "llm_returned_empty"})
        continue
    successful_chunks += 1
    ...

"metadata": {
    "total_chunks": total_chunks,
    "successful_chunks": successful_chunks,
    "failed_chunks": len(failed_chunks),
    "failed_chunk_details": failed_chunks,
    "success_rate": successful_chunks / total_chunks if total_chunks else 0.0,
}
```

并把 `success_rate < 阈值` 作为**任务失败**上报，而不是"完成"。

### 缺陷 4：子串模糊解析会静默错配类

**位置**：`extractor.py:1014-1030`，`resolve_to_det_id()`

```python
for lbl, did in label_to_det_id.items():
    if raw in lbl or lbl in raw:        # ← 子串双向包含
        return did
```

**中文子串匹配的陷阱**：

| LLM 返回的 source | 已存在的类 | 匹配结果 | 是否正确 |
|---|---|---|---|
| `投资者` | `机构投资者` | 匹配到 `机构投资者` | ❌ 错（少了"机构"限定） |
| `产品` | `理财产品` | 匹配到 `理财产品` | ❌ 错 |
| `银行` | `中国工商银行` | 匹配到 `中国工商银行` | ❌ 错 |
| `附件` | `附件A` | 匹配到 `附件A` | ❌ 错 |

而 `dict` 的迭代顺序决定"先匹配到哪个"——**结果不确定**。这会让 link_type 的 source/target 挂到错误的类上，且**没有任何告警**（`resolve_to_class_name` 成功返回，不会走 `logger.warning` 那条丢弃分支）。

**修法**：删掉子串匹配，改成严格三级

```python
def resolve_to_det_id(raw: str) -> Optional[str]:
    if not raw:
        return None
    raw = raw.strip()
    # 1) 精确：id / name / label
    if raw in all_object_types:            return raw
    if raw in name_to_det_id:              return name_to_det_id[raw]
    if raw in label_to_det_id:             return label_to_det_id[raw]
    # 2) 归一化后精确（NFKC + 去空白 + 大小写）
    key = normalize_label_for_merge(raw)
    if key in norm_index:                  return norm_index[key]
    # 3) 别名表（从 schema 的 aliases/synonyms 字段读，需在阶段 A 让 LLM 输出）
    if raw in alias_index:                 return alias_index[raw]
    # 4) 长 label 的编辑距离兜底（仅 >= 4 字且距离 <= 1，防"投资者/投资方"类噪声）
    if len(raw) >= 4:
        cands = [d for k, d in norm_index.items()
                 if abs(len(k) - len(key)) <= 1 and edit_distance(k, key) <= 1]
        if len(cands) == 1:
            return cands[0]
    # 5) 匹配不上 → 明确失败，让调用方记录并丢弃（保持现有 warning 行为）
    return None
```

**并建议**：在 `extract_schema` 的 JSON Schema 里给 `object_types` 加 `aliases: string[]` 字段，让 LLM 主动给出同义词，供第 3 步使用。

## 二、🟠 P1 性能缺陷

### 缺陷 5：分块抽取完全串行（最大提速点）

**位置**：`extractor.py:3529`（async）/ `:1418`（sync）

```python
for i, chunk in enumerate(chunks):
    check_cancelled()
    ...
    data = await self._async_call_llm(system_prompt, user_prompt, ...)   # ← 逐个 await
```

`async_extract_instances` 名字里带 async，但**没有任何并发**——它只是把阻塞调用换成了可等待调用，分块之间严格串行。

**量化**：一份 300 页中文文档，按 `chunk_size=15000` 约切 30–50 块；单块 LLM 抽取（含 16000 max_tokens 输出）保守按 45s 计 → **22–37 分钟纯等待**。期间 GPU/推理服务利用率极低。

**修法**：两阶段（先并发调 LLM，再按序合并）

```python
EXTRACT_CONCURRENCY = int(os.getenv("EXTRACT_CONCURRENCY", "8"))

async def _extract_one(idx: int, chunk: dict):
    async with EXTRACT_SEMAPHORE:                 # 全局并发上限
        chunk_text = chunk.get("text", "") if isinstance(chunk, dict) else chunk
        chunk_filename = chunk.get("filename", "unknown") if isinstance(chunk, dict) else "unknown"
        head = f"【文档来源】: {chunk_filename}\n" if chunk_filename != "unknown" else ""
        prompt = head + user_prompt_template.format(chunk=chunk_text)
        try:
            data = await self._async_call_llm(system_prompt, prompt, task_id=task_id,
                                              json_schema=INSTANCE_EXTRACTION_JSON_SCHEMA)
        except Exception as e:
            logger.error(f"[InstanceExtraction] 分块 {idx+1} 失败：{e}")
            data = None
        return idx, chunk_text, chunk_filename, data

# ① 并发执行所有分块
results = await asyncio.gather(*[_extract_one(i, c) for i, c in enumerate(chunks)])

# ② 按 chunk_index 排序后串行合并 —— 保证合并顺序确定、结果可复现
results.sort(key=lambda r: r[0])
for idx, chunk_text, chunk_filename, data in results:
    ...原有合并逻辑...
    report_progress((idx + 1) / total_chunks, f"合并分块 {idx+1}/{total_chunks}")
```

**关键点**：

- **合并必须串行且按序**。当前 `all_instances` 的合并语义依赖顺序（先到的 label 决定 `type` 和 `_source_quote`）。并发直接写会引入竞态和不可复现的结果。所以是「并发取数 + 串行合并」。
- **并发上限要可配**。本地 vLLM 可以开到 16–32；远程限流 API 可能只能 2–4。做成环境变量 + 可选自适应（遇到 429 自动降并发）。
- 顺带把 `request_interval` 的 `time.sleep(2)`（`:1001`）去掉——并发化之后这个"限速"没意义了，真正的限速交给 semaphore。

**预期收益**：并发 8 → 30–50 块耗时从 ~30 分钟降到 **~5 分钟**。

### 缺陷 6：关系解析 O(n²) 全量扫描

**位置**：`extractor.py:1568-1579`（sync）、`:3580+`（async 同构）

```python
if t_raw in all_instances:          # ← 几乎永远 False：t_raw 是 label，all_instances 的 key 是 det_id
    valid_targets.append(t_raw)
else:
    for existing_id, existing_inst in all_instances.items():        # ← 全量线性扫描
        if names_are_similar(t_raw, existing_inst.get("label", "")):
            ...
```

第一个判断 `t_raw in all_instances` 基本无效（`det_id` 形如 `I_a1b2c3d4`，LLM 返回的是中文 label），所以**每条边的每个目标都会触发一次全量扫描**。

复杂度：`O(实例数 × 每实例关系数 × 每关系目标数 × 已有实例数)`。1 万实例、平均 3 条关系、每条 1.5 个目标 → **约 4.5 亿次字符串比较**。这就是"实例一多就卡住"的根因。

**修法**：建归一化 label 索引

```python
# 在循环外初始化
label_index: Dict[str, str] = {}          # 归一化 label → det_id

def index_instance(det_id: str, label: str):
    key = normalize_label_for_merge(label)
    label_index.setdefault(key, det_id)   # 首次写入优先，保持与串行语义一致

# 插入新实例时
if det_id not in all_instances:
    all_instances[det_id] = {...}
    index_instance(det_id, raw_label)

# 查目标时
key = normalize_label_for_merge(str(t_raw))
resolved = label_index.get(key)
valid_targets.append(resolved if resolved else str(t_raw))
```

**兜底**：模糊匹配（编辑距离/向量）不要在热路径里做，抽出来做一次**批处理实体消解**（见缺陷 10），成本从 O(n²) 降到 O(n log n)。

### 缺陷 7：抽取跑在 API 事件循环里

**位置**：`api/ontology.py:32`、`:393`、`:564`、`:856`、`:1121`

```python
EXTRACTION_SEMAPHORE = asyncio.Semaphore(3)      # 模块级 = 每进程 3 个
...
async def run_extraction():
    async with EXTRACTION_SEMAPHORE:
        schema = await extractor.async_extract_schema_only(...)
        ...
asyncio.create_task(run_extraction())            # ← fire-and-forget，跑在 API 进程
```

**四个问题**：

1. **CPU 密集段阻塞事件循环**：切分（`_recursive_split` 递归 + 字符串拼接）、合并（O(n²) 扫描）、`rdflib` 解析 TTL、`schema_to_graph_data` —— 这些是纯 CPU 同步代码，在 event loop 里执行会**卡住所有 HTTP 请求**。一个 300 页文档的合并阶段可能卡 10s+，期间所有用户的操作都超时。
2. **任务丢失**：`asyncio.create_task` 没有持久化。API 进程重启 / 滚动更新 → 所有在跑的抽取任务**无声消失**，用户只看到进度条永远停在 40%。
3. **无法水平扩展**：`Semaphore(3)` 是进程级的。起 4 个 API 副本 → 实际并发 12，且任务是"粘"在收到请求的那个副本上的，扩缩容会打断任务。
4. **无重试**：失败即失败，没有断点续跑。

**修法**：把抽取移到独立 worker

```
推荐方案：Celery + Redis
  api  →  只做鉴权 + 参数校验 + 投递任务 + 返回 task_id（202）
  worker-extract  →  独立进程池，跑 LLM 抽取（IO 密集，可高并发）
  worker-parse    →  独立队列，跑文档解析 / VL（CPU/GPU 密集）
  worker-graph    →  独立队列，跑合并 / 消解 / TTL 生成 / Neo4j 写入

任务状态落 MySQL（task_manager 已有雏形），支持：
  · 进程重启后任务可恢复（重新入队或标记失败）
  · 断点续跑（记录已完成 chunk 索引，重跑时跳过）
  · 水平扩展（加 worker 副本即可）
```

**如果暂时不想引入 Celery**，最低成本的过渡方案：把 CPU 密集段挪出事件循环

```python
# 至少让合并/切分不阻塞 API
import anyio
result = await anyio.to_thread.run_sync(heavy_merge_function, ...)
```

但任务丢失和无法扩展这两个问题，只有独立 worker 能解。

### 缺陷 8：chunk_size=15000 字符过大

**位置**：`extractor.py:387,668,1155` 默认 `chunk_size=15000`

**问题**：

| 方面 | 问题 |
|---|---|
| 中文 token 比 | 15000 中文字符 ≈ 15000–22000 token（视 tokenizer）。加上 system_prompt（`extract_schema` 的 system prompt 本身约 2500 字符）+ JSON schema 约束，单次请求轻松超过 24k token |
| 输出侧 | `max_tokens=16000`（`llm_client.py:182`），要求一个 15000 字符的 chunk 产出所有对象类型 + 属性 + 关系，**长 JSON 极易被截断**（虽然有 `_repair_truncated_json` 兜底，但修复的是语法，不是丢失的语义） |
| 实例数上限 | prompt 里写"每个 chunk 最多提取 15 个实例"——15000 字符里通常有远超 15 个实体，**硬上限直接导致漏抽** |
| 重叠 | `chunk_overlap=10`（百分比）→ 1500 字符重叠。比例合理，但基数太大导致重复内容多 |

**修法**：

```python
# 按语言给不同默认值，并按 token 而非字符计数
CHUNK_DEFAULTS = {
    "zh": {"chunk_size": 2000, "chunk_overlap_pct": 12},   # ≈ 2000-2800 token
    "en": {"chunk_size": 3000, "chunk_overlap_pct": 12},
}
# 上限保护：超过 max_chars_per_chunk 直接报错，不静默接受
```

同时把 prompt 里的"最多 15 个实例"改成与 chunk 大小联动的动态值，或者**去掉硬上限、改成"不要重复、不要推测"**（上限本身是漏抽的直接原因）。

> 注意：调小 chunk_size 会让分块数变多，但配合缺陷 5 的并发化，总耗时反而下降。

### 缺陷 9：无 LLM 结果缓存

全局搜索 `cache` / `lru_cache`，`services/` 和 `infrastructure/` 下**没有任何 LLM 结果缓存**。

后果：同一份文档重跑（改了 user_intent、改了 chunk_overlap、想对比两次结果）→ **全额重新烧 token**。开发调试阶段这是最贵的浪费。

**修法**：

```python
# 在 _call_llm / _async_call_llm 外包一层
def _cache_key(self, system_prompt: str, user_prompt: str) -> str:
    h = hashlib.sha256()
    for part in (self.llm_client.model, system_prompt, user_prompt):
        h.update(part.encode("utf-8"))
    return f"llm:cache:{h.hexdigest()}"

# Redis，TTL 7 天；命中直接返回
# 注意：json_schema 变了要进 key；temperature > 0 时慎用
```

### 缺陷 10：实体消解太弱

**位置**：`extractor.py:209-216`（`names_are_similar`）、`:636-658`（`_normalize_term`）

```python
def names_are_similar(name1: str, name2: str) -> bool:
    n1 = _to_snake_case(name1).replace('_', '')     # 对中文完全无效
    n2 = _to_snake_case(name2).replace('_', '')
    if n1 == n2: return True
    if name1.strip() == name2.strip(): return True  # 等价于精确匹配
    return False
```

`_to_snake_case` 是给驼峰英文用的，对中文是恒等变换。所以**中文实体消解退化成精确字符串匹配**。

`_normalize_term` 只有 6 条后缀规则（`的人/的人员/人员/的人士/的情况/的记录`），覆盖极窄。

**实测不会合并的例子**：

| A | B | 应该合并？ | 现状 |
|---|---|---|---|
| 投资者 | 投资人 | ✅ | ❌ 不合并 |
| 中国工商银行 | 工商银行 | ✅ | ❌ 不合并 |
| 北京华信科技有限公司 | 北京华信科技 | ✅ | ❌ 不合并 |
| 理财产品 | 理财 产品 | ✅ | ❌ 不合并（有空格） |
| 北京市 | 北京市政府 | ❌ 不该合并 | ✅ 不合并（侥幸） |

**修法**：三层消解，从便宜到贵

```python
# 第 1 层：确定性归一（O(1)，覆盖 60% 场景）
def normalize_entity(name: str) -> str:
    s = unicodedata.normalize("NFKC", name).strip().lower()
    s = re.sub(r"\s+", "", s)                                  # 去所有空白
    s = re.sub(r"[（）()【】\[\]「」]", "", s)                    # 去括号
    for suf in ("股份有限公司", "有限责任公司", "有限公司", "公司",
                "集团有限公司", "集团"):
        if s.endswith(suf) and len(s) > len(suf) + 1:
            s = s[: -len(suf)]
            break
    return s

# 第 2 层：别名表（人工 + LLM 产出，覆盖简称/全称/曾用名）
#   在 extract_schema 的 JSON Schema 加 aliases 字段，让 LLM 主动给同义词
#   存 MySQL 一张 entity_aliases 表，可人工维护

# 第 3 层：向量 + 拼音 blocking（覆盖变体）
#   · 拼音首字母 blocking：pypinyin 已在 requirements 里
#     key = "".join([p[0] for p in lazy_pinyin(name)])
#   · 向量相似度：复用已有的 embedding 服务
#   · 阈值策略：>= 0.92 自动合并；0.80~0.92 标人工复核；< 0.80 不合并
#   · 类型必须一致才允许合并（跨类型合并几乎总是错的）
```

**注意**：中文短实体（< 4 字）向量区分度低，应**降低向量权重、提高规则权重**。

### 缺陷 11：溯源只存 chunk 前 200 字符

**位置**：`extractor.py:1466`（sync）、`:3571`（async）

```python
inst["_source_quote"] = chunk_text[:200] if chunk_text else ""
```

`chunk_text` 长度可达 15000 字符，但溯源只取**开头 200 字符**。实体出现在 chunk 中后部时，这条"溯源"记录指向的内容与实体**完全无关**。

这直接违背了"可溯源"这个核心卖点——用户点开实体看到的"原文出处"是错的。

**修法**：让 LLM 返回证据片段

```python
# 1) 在 INSTANCE_EXTRACTION_JSON_SCHEMA 的 instances 项里加字段
"evidence": {
    "type": "string",
    "description": "该实例在原文中出现的原句（必须逐字引用，不超过100字）"
}

# 2) prompt 里明确要求
"7. 【溯源】每个实例必须提供 evidence 字段，逐字引用原文中包含该实体的句子。"

# 3) 兜底：LLM 没给 evidence 时，用实体 label 在 chunk 里定位
def locate_quote(chunk_text: str, label: str, window: int = 80) -> str:
    idx = chunk_text.find(label)
    if idx < 0:
        return chunk_text[:200]          # 真找不到才退回开头
    return chunk_text[max(0, idx - window) : idx + len(label) + window]

# 4) 更彻底的方案：让 LLM 同时返回 char_start/char_end 偏移
#    （要求 LLM 做精确偏移不可靠，但可做校验：偏移处的文本是否等于 label）
```

**顺带**：`extract_schema` 因为缺陷 2，`filename` 恒为 `unknown`，schema 层的溯源是完全缺失的。

### 缺陷 13：中文分隔符带尾空格

**位置**：`extractor.py:414, 485`

```python
separators=["\n\n", "\n", "。 ", "！ ", "？ ", ". ", " ", ""]
```

`_recursive_split` 的选分隔符逻辑是 `if s in text: separator = s` —— **要求字面匹配**。中文文档里句号后通常**没有空格**（"这是第一句。这是第二句。"），所以 `"。 "` 永远不命中，`"！ "` `"？ "` 同理。

实际效果：只要文本里有 `\n`，就会用 `"\n"` 切；如果连 `\n` 都没有（比如从 PDF 抽出的连续中文），一路退化到 `" "` → `""`，**按固定字符数硬切**，句子被拦腰截断。

**修法**：

```python
separators=["\n\n", "\n", "。", "！", "？", "；", "…", ". ", "! ", "? ", " ", ""]
#                      ↑ 去掉尾空格，补中文分号/省略号
```

**更好的做法**：中文走专门的分句状态机（处理句末标点 + 收尾引号 + 省略号），而不是靠 `str.split`。参考实现要点：

```python
def split_sentences_zh(text: str) -> List[str]:
    END = "。！？!?…"
    CLOSERS = "”’」』）)】》"
    parts, buf, i, n = [], [], 0, len(text)
    while i < n:
        ch = text[i]; buf.append(ch)
        if ch in END:
            while i + 1 < n and text[i + 1] in END:      # 吞连续标点（"……" "？！"）
                i += 1; buf.append(text[i])
            while i + 1 < n and text[i + 1] in CLOSERS:  # 吞收尾引号
                i += 1; buf.append(text[i])
            parts.append("".join(buf).strip()); buf = []
        i += 1
    if buf: parts.append("".join(buf).strip())
    return [p for p in parts if p]
```

### 缺陷 14：VL 解析全页渲染 + 串行

**位置**：`vl_parser.py:71-82`（渲染）、`:99-107`（组包）、`:181-195`（批次循环）

**三个问题**：

1. **全页无条件渲染**：`for page_num in range(len(doc))` 把**每一页**渲成 PNG（`VL_DPI` 缩放）。300 页 PDF → 300 张 PNG 落盘。即使绝大多数页有完整文本层、根本不需要 VL，也照样渲染。
2. **base64 内联**：`data:{mime};base64,{b64}`，比原图**膨胀 33%**，且全部塞进单次请求的 messages 里。`VL_BATCH_SIZE` 张图一次发 → 请求体可能几十 MB。
3. **批次串行**：`for batch_start in range(0, len(page_images), VL_BATCH_SIZE)` 逐批 `_call_vl_model`，无并发。

**修法**：

```python
# 1) 只渲染"文本层为空/过少"的页 —— 这是最大的节省
def _pages_needing_vl(pdf_path: str, min_chars_per_page: int = 50) -> List[int]:
    doc = fitz.open(pdf_path)
    need = []
    for i, page in enumerate(doc):
        if len(page.get_text("text").strip()) < min_chars_per_page:
            need.append(i)
    doc.close()
    return need

# 2) 并发批次
import asyncio
results = await asyncio.gather(*[_vl_batch(b, prompt, cfg) for b in batches])
# 注意按 batch_start 排序后拼接，保持页序

# 3) 优先用 URL 而非 base64：若 VL 服务能访问对象存储，传 presigned URL
#    无法用 URL 时，降低 DPI（150 通常足够识别正文）+ 用 JPEG 质量 85 代替 PNG
```

**另外**：`subprocess.run(["file", "--mime-type", ...])`（`:132-138`）依赖 `file` 命令，**Windows 上不存在**，异常被 `except Exception: pass` 吞掉后静默回退到扩展名判断。当前是在 Linux 容器里跑所以没暴露，但本地开发会静默降级。建议直接 `import magic` 或用扩展名 + 文件头魔数判断。
