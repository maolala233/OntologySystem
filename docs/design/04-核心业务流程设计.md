# 04 · 核心业务流程设计

> 覆盖需求 2/3/4/8 的"怎么做"：解析管道、中文切片、两阶段构建（SchemaGate + promote）、实体消解三层、冲突检测、溯源、审核队列、版本与时间轴、发布、中文专项、抽取链路 14 缺陷修复对照。
>
> 所有 LLM/嵌入/视觉模型均经 `adapters/provider.py` 按 `model_configs` 解析（见 03 §5）。

## 1. 端到端流程（与 01 §7 对应，本册展开每段）

```
[上传] → sha256 秒传判定 → MinIO 落桶
  → [解析] backend 选择 → OCR 判定 → 全文 Markdown 化 → 语言检测
  → [切片] 中文分句状态机 → chunk(2000/15%) → document_chunks
  → [Schema 阶段] 分块并行 LLM 抽取(类型/属性/关系) → 归并去重 → SchemaGate 归一
      → 画布人工修订(现有交互) → 版本 v{n}(schema)
  → [Instance 阶段] SchemaGate 闸门抽取 → 证据定位 → 行表落库
  → [消解] 三层流水线 → 合并/生成审核项
  → [冲突] 5 类检测 → 生成审核项
  → [审核] 人工裁决 → 落地合并/回写 → outbox
  → [同步] Neo4j/Milvus(worker-graph) + Oxigraph(worker-rdf)
  → [版本] 快照 → [发布] publications → 公共区只读
```

## 2. 文件解析管道（需求 3）

### 2.1 格式 × 后端矩阵（`adapters/parsing.py`）

| 格式 | 首选 backend | 兜底 | 备注 |
|------|-------------|------|------|
| PDF 文本型 | docling | pymupdf4llm（现有 `parser.py:311`） | 版式复杂/多栏/表格时 docling 明显更优 |
| PDF 扫描件/图片 | docling(enable_ocr=True) | **VL 视觉模型**（现有 `vl_parser.py` 改造） | 判定见 §2.2；无 docling 环境时 VL 是主路径 |
| DOCX/DOC | docling → python-docx | LibreOffice→PDF→VL（现有路径保留） | |
| PPTX | python-pptx（现路径） | docling | 讲义类常见，保留表格/备注提取 |
| XLSX/XLS/CSV | 现有 `_parse_excel`（合并单元格/表头检测保留） | pandas | 输出 Markdown 表格 |
| MD/TXT/JSON | 原生 | — | |
| HTML | docling | BeautifulSoup | |
| TTL/OWL/RDF | **OntologyIngestor 直导入**（新增能力） | 现有 `convert_ttl_to_graph_data` | 支持导入既有本体作为起点 |

### 2.2 扫描件判定（修复缺陷 #14 的"全页无条件渲染"）

```
parse_document:
  1. 先走快速文本层（pymupdf 每页抽取）
  2. 判定：avg(每页可见字符) < 50 或 图片占比 > 60% → 判定为扫描件
  3. 扫描件 → docling OCR（首选）；docling 不可用 → VL 模型批处理：
     - 仅渲染"文本稀疏页"（而非全页），150 DPI，3 页/批
     - 图片直接送 VL；不再 base16→base64 全量内联（改 MinIO 预签名 URL 传给多模态 API 或分批 base64）
     - 并行批处理（asyncio.Semaphore(2)），替代现串行
  4. 每页产出 {page_no, text_md, ocr_used} → 拼全文
```

### 2.3 中文切片（`adapters/chunking.py`，替代 `extractor._chunk_text`）

- **策略**：Semantica `TextSplitter` 的 `recursive` 为主，**分隔符序列改为中文优先**：`["\n\n", "\n", "。", "！", "？", "；", ".", " "]`（修复缺陷 #13 的 `"。 "` 尾空格 bug）。
- **中文分句状态机**（sentence 边界判定，供 semantic/entity_aware 策略与溯源定位共用）：

```
state ← NORMAL
for ch in text:
    if ch in '。！？；' and state != QUOTE: flush_sentence()
    elif ch == '”' and state == QUOTE: state ← NORMAL; flush_sentence()
    elif ch == '“': state ← QUOTE
    elif ch in '…—' and next not in same: flush_sentence()
```

- **参数**：`chunk_size=2000` 字符（中文），`chunk_overlap=15%`；`entity_aware` 策略用于实体密集文档（保证实体跨度不跨块）——抽取 prompt 同时携带前块 100 字符上下文做衔接。
- 每块记录 `char_start/char_end`（原文偏移）——溯源定位与前端高亮的基础。
- 表格/代码块不切断（structural 标记，从 docling 的结构化输出继承）。

### 2.4 解析产物

全文 Markdown → MinIO `ontology-parsed/`；语言检测（langdetect）写 `uploaded_documents.language`；`parse_backend` 记录实际链路；失败隔离：单文档失败不影响同批其他文档（现有 `continue_on_error` 语义保留）。

## 3. Schema 阶段（TBox）

### 3.1 流程

```
for chunk in chunks (Celery chord 并行, parallelism=4):
    prompt = 骨架抽取模板(chunk, 已发现类清单, 输出 JSON Schema 约束)
    → LLL(extract 用途默认模型, structured output)
    → 本地校验(jsonschema) → 失败重试 1 次(带错误反馈) → 仍失败计 warning
归并: 类合并(label_normalized, 修复缺陷 #2: 不再把原始 dict 塞 prompt;
      结构化字段化传入; 归并键 = label + 定义向量余弦>0.92 可选)
SchemaGate 归一: 类型名规范化(去空格/统一全半角/首字母大写规则仅对 ASCII)、
      ObjectProperty domain/range 必须引用已存在类(悬空→建占位类标记 pending)
产物: entities(is_class_node=1) + relations(is_class_edge=1) → 版本(kind=schema)
```

- 并行修复缺陷 #5：分块并行度 `parallelism` 默认 4（extract 队列 concurrency=2 × 2 协程）。
- LLM 输出缓存：`(model, prompt_hash)` → Redis 8h TTL，重跑不重复计费（修复缺陷 #9）。
- `bootstrap_schema` 用法：冷启动无文档时，用户粘贴领域描述文本 → 产出草案 TBox（`draft: true`）进画布人工修订，绝不自动应用（Semantica 约定）。

### 3.2 画布人工修订（保留现有交互）

前端在骨架编辑 Tab 修改类/关系 → `POST /extraction/schema/revise` 提交 diff → 服务端校验（类名唯一、关系 domain/range 有效）→ 行表更新 → outbox 同步。**修订自动产生版本**（kind=schema，label="画布修订"）。

## 4. Instance 阶段（ABox）

### 4.1 严格闸门 + 证据

```
for chunk:
    prompt = 实例抽取模板(TBox 摘要: 类/属性/关系清单, chunk, 前块上下文)
    → LLM structured output
    → SchemaGate 校验:
        class ∈ TBox 类集 → 否则按 promote_policy 处理(03 §8)
        object property 谓词 ∈ TBox 属性集 且 domain/range 类型匹配
          (修复缺陷 #4: 精确匹配, 废除子串双向包含)
    → 证据定位: 要求 LLM 对每个实体返回 evidence(原句) + 用 char 偏移二次校验
      (locate_quote: 在 chunk 文本中检索 evidence 子串, 失败→evidence 降级为 chunk 摘要并标 missing_evidence 审核项)
    → 实体落行表: uri = {base}/individual/{md5(label+class)[:16]}
      (修复缺陷 #3: confidence 为 LLM 自报值, 不再伪造 metadata 成功率)
```

### 4.2 类型匹配（修复缺陷 #4 详解）

废除 `extractor.py:1027` 的子串双向包含判定，改为：
1. 精确匹配 `label == class`；
2. 归一化匹配（全半角/空白/大小写）；
3. 别名表命中（TBox 类的 `aliases`，画布修订时可维护）；
4. 以上皆不中 → SchemaGate 违例路径（§4.1）。

### 4.3 产物与统计

任务完成返回：`{instances, relations, discarded_count, promote_count, missing_evidence_count, chunks_processed}`；`project.status=building→ready`；自动落版本（kind=full）。

## 5. 实体消解三层流水线（需求 4，`adapters/resolution.py`）

> 修复缺陷 #1（前缀去重误合并）与 #10（中文消解失效）的系统性方案。废除 `names_are_similar` 与前缀分组正则（`extractor.py:2064-2115`）。

```
第 1 层 确定性归一 (label_normalized):
    去首尾空白 → 全角→半角 → 统一大小写 → 去装饰符号(·-) → NFKC
    同 label_normalized + class_label → 必合并（高置信）
第 2 层 拼音 blocking (中文专属):
    pypinyin 生成拼音键（全拼+首字母两种）+ 编辑距离(jaro_winkler≥0.9 或 leva≤2)
    + 同 class_label → 候选对（"腾讯"~"腾讯公司" "中国人民银行"~"央行"需别名表）
第 3 层 向量相似 (语义层):
    bge-m3 嵌入(label+class+属性拼接) 余弦 ≥ 0.85 → 自动合并
    0.60 ≤ 相似度 < 0.85 → review_items(entity_merge) 转人工
    < 0.60 → 放行
```

- **合并执行**（Semantica `EntityMerger` 语义 + 平台持久化）：`canonical_id` 指向保留实体；属性合并策略默认 `keep_most_complete`，可按属性配置（`merge_strategy_manager` 每属性规则）；被合并实体 `status=merged`、`canonical_id` 指向 canonical；**关系迁移**：指向 merged 实体的 relation 全部改指 canonical（同 (s,p,o) 去重）。
- **可逆**：合并历史存 `review_items(result_ref)` + `audit_logs`；`POST /resolution/split` 可拆分。
- **溯源保留**：合并后 `provenance_records` 指向 canonical，保留各来源记录（`preserve_provenance=True` 语义）。
- **增量**：新抽取批次只与新批次 + canonical 池比对（`incremental_detect`），不全量重算。

## 6. 冲突检测（需求 4，`adapters/conflicts.py`）

| 冲突类型 | Semantica 支持 | 平台实现 | 产物 |
|----------|---------------|---------|------|
| VALUE（同实体同属性值矛盾） | ✅ detect_value_conflicts | 直接接入 | review_items(conflict_value)，附各来源+可信度 |
| TYPE（同实体多类型） | ✅ detect_type_conflicts | 直接接入；结合 SchemaGate 后应趋零 | conflict_type |
| RELATIONSHIP（关系矛盾，如 A→B 与 A↛B） | ✅ detect_relationship_conflicts | 直接接入 | conflict_relationship |
| TEMPORAL（时间线矛盾） | ⚠️ 枚举有、检测未实现 | 自建：对带 `valid_from/valid_until` 属性的实体做区间重叠/包含检查 | conflict_value(payload.kind=temporal) |
| LOGICAL（公理矛盾） | ⚠️ 未实现 | 自建：SHACL 校验（`adapters/exporting` 生成 shapes + `OntologyValidator`）失败项转审核 | review_items(new_class/低优先) |

- 来源可信度：`SourceTracker.set_source_credibility` —— 默认全部 1.0；管理员可按文档/批次调权；解决策略默认 **CREDIBILITY_WEIGHTED**，高严重度（critical）强制 MANUAL_REVIEW。
- `InvestigationGuideGenerator` 输出附在审核项 payload.guide（调查步骤 + 建议动作），审核 UI 直接渲染。
- 冲突检测时机：消解之后（消解减少假冲突）；抽取批次完成时自动跑 VALUE/TYPE/RELATIONSHIP 三类，TEMPORAL/LOGICAL 手动触发（03 §9）。

## 7. 人工审核队列（需求 4）

### 7.1 8 种触发原因（`review_items.item_type`）

| item_type | 触发 | 典型 payload |
|-----------|------|-------------|
| entity_merge | 消解第 3 层 0.60–0.85 区间 | `{candidates:[{id,label,class,evidence}...], similarity, suggestion:"merge"}` |
| new_class | ABox 新类型 promote_policy=review | `{label, occurrences, sample_evidence[], suggested_domain_range}` |
| low_confidence_entity | confidence < 0.70 的实例 | `{entity, evidence, char_range}` |
| low_confidence_relation | confidence < 0.70 的关系 | 同上 |
| conflict_value / conflict_type / conflict_relationship | §6 三类 | `{conflicting_values, sources, severity, recommended_action, guide}` |
| missing_evidence | evidence 定位失败 | `{entity, chunk_ref}` |

### 7.2 状态机与规则

```
pending ──claim──▶ claimed ──decide──▶ approved | rejected | edited
   ▲                                        │
   └────── 超时未处理(beat 7天) 回收 ─────────┘
```

- 优先级：critical（冲突 severity=critical）> high（conflict_*）> medium（merge/new_class）> low（missing_evidence）。
- 批量裁决：同类型同动作 ≤50；`entity_merge` 批量仅允许 approve（逐项 similarity≥0.75 校验）。
- 裁决落地即产生 outbox 事件（合并→entity.merge；新类→class.upsert + 版本更新提示）。
- **发布门禁**：存在 pending/claimed 的 critical/high 审核项时禁止发布（03 §12）。

## 8. 溯源（需求 4，`adapters/provenance.py`）

- **采集**：抽取时每实体/关系强制写 `provenance_records`（document/chunk_index/evidence/char 偏移/method）；消解合并与审核修订产生 `method=merge/manual` 记录。
- **校验和**：SHA-256(`storage_key|char_start|char_end|evidence_text`)，防篡改与漂移（复用 Semantica `compute_checksum`）。
- **RDF 投影**：worker-rdf 写 `prov` 命名图：`onto:entity_X prov:wasDerivedFrom doc:D ; prov:hadMember chunk:C`（PROV-O）。
- **消费端**：
  - 图谱探索：节点详情面板展示来源列表 → 点击跳转文档预览并高亮 char 区间；
  - 问答引用：`[1][2]` 每条带 `{file, quote, char_range, preview_url}`；
  - 导出 html-report 附溯源附录。
- 修复缺陷 #11：evidence 是**实体所在原句**（LLM 返回 + 定位校验），不再是"chunk 前 200 字符"。

## 9. 版本控制与时间轴（需求 4，`adapters/versioning.py`）

| 时机 | 动作 |
|------|------|
| Schema 抽取完成 | 版本 v1（kind=schema） |
| 每次画布修订提交 | 版本（kind=schema, label=画布修订） |
| Instance 抽取完成 | 版本（kind=full） |
| 消解/审核批次落地 | 不落版本（记 audit），下个显式版本包含 |
| 手动 | `POST /versions`（用户自打标签） |
| 发布前 | 版本（kind=publication）+ graph_snapshots |
| 回滚前 | 版本（kind=rollback，先存 pre_rollback 快照） |

- **diff**：`versions/{a}/diff/{b}` —— 类/属性/实例/关系四级 added/removed/modified（字段级 from→to），复用 `OntologyVersionManager.compare_versions` + 行表对账。
- **回滚**：restore 目标版本 → 行表整体替换（事务）→ outbox 全量重建三类存储 → 新版本（kind=rollback）。任何回滚可再回滚（版本链不断）。
- **双时间轴**：`valid_from/valid_until`（业务有效时间，抽取时 LLM 识别或用户编辑）+ `recorded_at/superseded_at`（事务时间，行表自动维护）。`TemporalGraphQuery.query_at_time` 封装为 timeline API（03 §11），前端 vis-timeline 渲染（05 §6.7）。
- 快照存储：TTL（schema）与图 JSON（full）入 MinIO，行表只存 key + stats + checksum。

## 10. 发布（需求 4）

```
publish 校验链:
  知识域必填(沿用现有校验) → 无 critical/high 待审项 → 当前 TBox 健康检查
  (OntologyQualityGate: min_coverage / max_errors，只警告不阻断的项写入发布说明)
  → 落版本(kind=publication) → graph_snapshots(purpose=publication)
  → publications 记录 → RDF pub 命名图固化
公共区:
  /api/assets 只读 publications(status=published) → 快照投影
  资产中心只读视图（图谱/详情/导出），无任何写入口
  编辑器打开已发布项目 → 403 PUBLISHED_READONLY + 引导"取消发布或另起新版"
unpublish: 公共区下线；快照与 pub 命名图保留（历史可审计）
```

- [ ] 两阶段交互不变：抽骨架→画布修订→抽实例链路可用，且每步自动落版本
- [ ] SchemaGate：未定义类型按 promote_policy 三种模式行为正确
- [ ] 消解：金样本 F1 ≥ 0.85；误合并可 split 回滚
- [ ] 冲突：VALUE/TYPE/RELATIONSHIP 自动检出并生成审核项，critical 强制人工
- [ ] 审核：8 类触发原因、状态机、批量裁决、发布门禁生效
- [ ] 版本：diff/回滚/时间轴可用；回滚后三类存储一致（对账脚本通过）
- [ ] 发布：快照固化、公共区只读、PUBLISHED_READONLY 拦截生效
- [ ] 中文专项 9 项全部落地，金样本回归通过
