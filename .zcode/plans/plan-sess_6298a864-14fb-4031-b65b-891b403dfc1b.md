# OntologySystem × Semantica 平台设计方案（分册文档）

## 目标
在 `docs/design/` 下产出一套中文、生产级、可直接投喂大模型 vibe coding 的平台设计方案，覆盖用户提出的全部 8 项需求 + 图谱可视化优化（semantica-explorer 方案）。定位为**演进重构**：以现有代码库和已配备中间件（MySQL/Neo4j(n10s)/Redis/Milvus/业务MinIO/嵌入式Oxigraph）为基线，标注每个模块的现状→目标→改造点（涉及哪些现有文件）。本轮**只写文档，不改任何代码**。

## 调研结论（方案的事实基础）
- **Semantica v0.7.0** 是"引擎层"：解析（Docling OCR）、13 种切片、DuplicateDetector/EntityMerger、ConflictDetector（5 类冲突+7 种策略）、ProvenanceManager（W3C PROV-O+SHA-256）、TemporalVersionManager/OntologyVersionManager、Neo4j/Milvus/Oxigraph 等统一存储接口、18 种导出、semantica-mcp（stdio）、AgentContext GraphRAG。缺口：多用户 RBAC、模型配置 UI、审核工作台、任务编排、上传门户、中文 NLP（pattern NER/分句对中文无效）→ 全走 LLM 方法 + 中文分句预处理 + bge-m3。
- **semantica-explorer** 前端 = React19 + Sigma.js 3 + graphology(FA2/Louvain) + React Flow 12 + vis-timeline + Monaco，随 PyPI 分发、无 npm 组件库 → 正确路径是**移植其前端模块**（约 1500 行框架无关直搬 + 600 行改造）+ 自建游标分页数据契约，而非整站嵌入。
- **现有平台**：两阶段构建交互（骨架→画布审核→实例）是核心资产，保留；抽取链路有 14 项已知缺陷（4 个 P0）、图谱展示有 5 项硬伤（两套图实现重复、SVG 上限低、布局不可复现、无 LOD、中文标签截断）。仓库已有三份规划文档（semantica优化实施步骤/抽取优化方案/图谱展示重构方案），新方案与其兼容并在其基础上收敛为可执行蓝图。

## 关键设计决策（将固化进文档）
1. **Semantica 作为引擎，经适配层接入**：`app/adapters/` 13 个适配文件，业务层零直接依赖，保留现有两阶段交互只换引擎。
2. **任务编排**：Celery + Redis（中间件已备），extract/parse/graph 三队列 + worker-rdf 单并发；淘汰进程内 TaskManager。
3. **RDF 持久化**：嵌入式 pyoxigraph（命名图划分 TBox/ABox/溯源/发布快照），不用 HTTP 容器。
4. **中文路线**：抽取全走 LLM 方法、bge-m3 1024 维嵌入、中文分句状态机、chunk 2000、`isascii()` 归一化守卫。
5. **图谱**：移植 semantica-explorer 前端模块 + ReactFlow/Sigma 双模式 + 后端游标分页与预布局，不移植其 Python 后端。
6. **权限模型**：role 字段 + 14 个模块码授权矩阵 + 项目级角色；消灭用户名硬编码 admin 与无鉴权 v1 端点。
