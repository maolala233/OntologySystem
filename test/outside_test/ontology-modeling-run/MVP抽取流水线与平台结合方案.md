# ontology_mvp.py 抽取流水线说明与平台结合方案

> 基于 feat_simplify @ 0b946c0（2026-11-16）分析；实测数据取自项目 320/321/323-327（外网 glm-5-3 flash、内网 glm-5 满血各多轮）。
> 脚本位置：`test/outside_test/ontology-modeling-run/ontology_mvp.py`（约 1300 行，独立可跑，不依赖平台代码改动）。

---

## 一、定位

一条「**LLM 只做声明与评审、代码做全部体力活**」的本体抽取流水线。与传统"逐片喂给 LLM 抽取"的根本区别是**计费方式**：按结构付费，不按数据量付费——每个结构只问一次模型，数据行免费展开。实测同一对文档（xls 154 表 + xlsx 3 表，4459 行）：**7 次 LLM 声明 + 1.2s 代码展开**替代了数百次逐行调用。

---

## 二、八阶段流水线

```
A 解析 → B 研判 → C 建模声明 → D 确定展开 → E 叙事 → F 专家(F.2对账/F.5消解) → G 公理+TTL+SWRL → H 落平台+检索冒烟
```

### A 解析（0.4s，0 LLM）
- **输入**：任意多文件（`--files a.xls b.xlsx c.docx …`）
- **分发**：`.doc`→libreoffice 无头转 docx（保表格）→antiword 回退；`.xlsx/.xls`→openpyxl/xlrd（合并单元格回填）；`.docx`→python-docx（段落+表格）；`.pdf`→PyMuPDF 文本层；`.pptx`→含备注层；`.csv`/`.txt`/`.md`/`.json`→textish
- **输出**：每文件 `{sheets:[{headers,rows}], narrative:[行]}`，逐字证据带 `文件[sheet]行n` 指针
- **边界**：图片内文字零提取（纯截图 docx/扫描 pdf 触发「0 内容」告警）——平台有 docling OCR/VL 链可接（见 §四）

### B 研判（9-12s，1 次 LLM）
单次小卡（2KB）判定文档族类（本体应用/制度/叙事），决定后续通道权重与提示词取向。

### C 建模声明（54-76s，N 次 LLM，N=签名组数≤12）
- **输入**：每张表的表头 + 6 个样本行（约 1.1KB）
- **签名分组**：表头序列规范化后相同的表共享一次声明——154+3 张表收敛到 7 组，**声明数绑结构新颖度，不绑表数量**
- **输出**：`table_maps`（列→谓词映射、target_class、矩阵声明、规则列标记）
- 矩阵表自检重声明回路：声明后样本行干跑，0 产出则重新声明

### D 确定展开（1.1-1.2s，0 LLM）——性价比之王
代码逐行机械展开，无模型参与：
- 普通列 → 实例属性；低基数枚举列（distinct 1-12 且值短）→ 取值实体化+建边
- 编码形表头 ≥5 → 矩阵单元实例三向边（对应主体/对应列头/单元取值）
- 规则列（均值 ≥40 字长文本）→ 原文实例 + 受规则约束边 + `^[a-z_]` 命名惯例抽业务字段（大写开头=系统编码不抽）
- 同签名表按同一映射展开；实例上限 1600、单表软上限 1200 防失控

### E 叙事（0-s，按片 0-24 次 LLM）
非结构化文本按 `max_input_chars/2` 分批（默认 12000 字符），逐片抽类/实例/边/规则，上限 24 片防调用风暴。表格型文档此阶段为 0。

### F 专家评审（56-260s，3 次 LLM）
- **F 专家**：45KB 预算的采集卡追加式评审（禁删改只出补丁），挖漏规则/引用闭合提示/层次收编（顶类「业务对象」）
- **F.2 对账**：29 句式完备性清单逐句报有据/无据/待确认，同时产出 `add_terms`（T1 同义/T2 编码对照/T3 别名）喂给术语层
- **F.5 消解**：四层递进合并（见 §三.4），同名/编码合并+嵌入合并（bge-m3，编码形豁免防余弦虚高误并），跨类候选只进待确认绝不自动合

### G 公理+TTL+SWRL（31-63s，2-3 次 LLM）
- 公理生成（domain/range/subclass/disjoint）→ **三层防线**（数据反证/合法性闸/继承环）→ 过闸对**直接写进 TTL**（教训：闸不回写产物只是报表装饰）
- 函数性公理白名单制：≥3 主体且零多值违规才上（防 owlrl 静默 sameAs 强并）
- **真 SWRL**：规则形式化 1 次调用转「ClassAtom + 属性原子 → x∈派生类」分类规则；引用字段自动注册 dprop；**if_class 非类时按实例标签→类反查兜底**（同名跨类歧义宁拒）
- owlrl 物化 + owl:Nothing 冲突检测（实测 0 冲突）

### H 落平台+冒烟（17s，0 LLM）
- 新建平台项目→上传解析→graph_data 写 DB（含 schema/axioms/待确认）→ Neo4j 批量 UNWIND 同步
- 节点循环遍历 `inst_id` 全量键（**闭合补建个体一并落图**，实测 TTL=平台图 1200=1200 逐类零差）
- 检索冒烟两题验证 graph_node/edge/axiom/keyword 通道

**实测总耗时**：表格型 87-106s（单 xlsx）/ 254s（双文档 flash）/ 340-488s（双文档满血 glm-5）；docx 叙事型 131s。

## 三、核心抽取规则（机制清单）

| # | 机制 | 判据（全部统计/结构特征，无业务词） | 作用 |
|---|---|---|---|
| 1 | 签名分组声明 | 表头元组规范化后相等 | 声明数=结构数，154 表→7 调用 |
| 2 | 形态驱动展开 | distinct 数、均值长度、编码正则 | 枚举/矩阵/规则/属性四形态自动分流 |
| 3 | 编码形识别 | `^[A-Za-z0-9]{4,12}$` 含数字 | 消解多数类统一；嵌入层豁免防 bge-m3 短码虚高 |
| 4 | 命名惯例字段抽取 | `^[a-z_]` 开头才抽业务字段 | camelCase/snake_case 与系统编码区分 |
| 5 | 消解四层 | 归一化同名→编码形多数类→跨类候选只进待确认→嵌入(同类≥0.96) | 误并防线（60 实例拼音事故底线：拼音层永不自动合） |
| 6 | 跨文档证据指针 | 逐实例 `_files` 追踪 | 主数据文档定义+场景文档引用→同一 URI（实测 27-28 双文件实例） |
| 7 | 公理三层防线 | 数据反证+合法性闸+继承环，过闸落图 | 推理真实发生（继承实例化+owl:Nothing 检测有据） |
| 8 | 真 SWRL 双路径+兜底 | 属性原子走 RID 或自动注册 dprop；if_class 非类反查实例类 | 结构化分类规则 8-20 条落图 |
| 9 | SKOS 术语层 | T1 同义/T2 编码对照/T3 别名+消解异形标签 | altLabel/exactMatch，检索与对账共用 |
| 10 | 29 句式对账 | 固定完备性清单（对象/约束/术语/规则/流程/权限/CRUD） | 覆盖率量化+补丁合并 |
| 11 | 预算闸 | max_input_chars=12000/专家卡 45KB/实例 1600/声明组≤12 | 任何文档的最坏成本有界 |

## 四、与现有平台结合

结合原则：**脚本已验证的机制逐个移植进平台对应位置，平台基建（解析/模型配置/进度/RPM 闸）反过来供脚本复用**。已拉取的 0b946c0 提供了三个新基建。

### 4.1 移植清单（脚本 → 平台）

| 脚本机制 | 平台落点 | 优先级 |
|---|---|---|
| D 确定展开（签名分组+table_maps+形态分流） | `extract_tasks.py` structure_expand（修 M1 三 bug：映射晚一拍/分节表/行主体兜底） | **P0**——271 实测 66 边已证明价值，重建即生效 |
| H 节点遍历 inst_id（闭合个体落图） | 落图/投影环节的实例收集口径 | P1 |
| G 公理过闸落图（不落图=报表装饰教训） | 公理扫描→TTL/graph_data 写入链 | P1 |
| 真 SWRL 结构化+if_class 兜底 | 抽取后处理规则形式化步骤 | P2 |
| 函数性白名单+数据反证 | 公理建议（axiom_suggestions）现有防线补齐 | P2 |
| F.5 消解四层（拼音永不自动合） | resolution.py（拼音层已强制人审，其余层对齐脚本口径） | P2 |

### 4.2 平台基建 → 脚本复用

| 平台能力（含 0b946c0 新增） | 脚本受益 |
|---|---|
| `LLM_MAX_RPM` 发起速率闸（9b1dbe0，次/60 秒） | 并行化方案（§六.2）的配额护栏现成——脚本并行发声明/分片时直接按闸限速 |
| 指代消解并发化+逐切片上报（73b5e15） | F.5 移植到平台时的并发参照；脚本侧消解同样可并发化（62s→预估 15-20s） |

### 4.3 建议的整合形态（两步）

1. **短期（零平台改动）**：脚本作为平台「快速构建」旁路工具保留，产物经 H 段直接落平台（现状已通）。

## 五、QA 优化

### 5.1 已验证有效的现状
- 计数题可答（确定性展开给干净实例类型）：「接口有多少个」31/152/182 三轮全对——271 时代"计数题拒答"已成历史
- 公理落图后 QA 引用 axiom 通道做推理支撑（约束类问题答案带公理依据）
- 主动纠错能力：矩阵题会指出问题前提错误并给正确场景清单

### 5.2 待优化（按影响排序）

| 问题 | 根因 | 方案 |
|---|---|---|
| **计数口径漂移**：同问题 31 vs 182（类声明方差直接变答案方差） | 类锚定只命名字面类，兄弟类（同业务域）不进引用 | **类锚定后兄弟类展开**：沿 属于业务域/父类边上溯一层再下探，只收有实例类，限量 3-5 个，分数 0.9<字面 0.95；QA 提示词补「同域相关类分别报数并说明口径」 |
| **"接口做什么"答不出**（数据在、引用没带） | graph_node 引用只 quote 标签不带实例属性 | 引用粒度升级：类清单引用带 top 属性样例；实例节点引用带 3-5 个属性键值 |
| **QA 模型偶发空回复**（qwen3.5:9b 115s 后空内容） | QA 缺省行能力弱 | QA 模型行固定 glm-5-3 chat 行（model_config_id=12 实测稳定） |
| 长答案慢（100s+） | 多通道融合后 LLM 上下文大 | 引用预算上限+按 ref_type 分层配额 |

### 5.3 检索准确性专项

- **SKOS altLabel 进检索索引**：术语层已建但未接入向量化文本——接入后"信贷工厂/普惠信贷工厂"类异形词直接召回
- **axiom 通道保持**：互斥/函数性引用已在答案中承担"不得同时归入两类"类推理约束
- **闭合个体标注**：平台图中「闭合补建」来源标注让 QA 引用可区分原文实例与兜底实例
- **CQ 验证闭环**：内容级探针（数据共现/边存在性）而非 schema 绑定 SPARQL（形态漂移会导致记分不稳，教训已固化）

### 5.4 修复记录：2026-11-16 QA 锚定失效实测与修复（两轮）

**第一轮（ aliases 断链）**：UI 问「接口字段总共有多少个？」答"8 个接口定义表"——8 是引用里原文切片 Sheet 数，QA 退化成 LLM 数表格。诊断：类形态漂移（327 无「接口字段」类）→ 字面锚定 0 命中 → 类节点 aliases 空（SKOS 术语层没接进 graph_data）→ 类清单引用缺席。**修复**：H 段从 TTL 读 `skos:altLabel` 填类节点 aliases。

**第二轮（行表断链，更深一层）**：补填 aliases 后类清单仍缺席——327 的 **entities 行表 0 行**。根因：card["classes"] 含同名类条目 → H 段类节点循环 append 重复 id（C2×2、C21×2）→ 平台行表双写同事务撞唯一键整体回滚 → 字面锚定（查行表）+类清单实例枚举（查行表）全空。324/325 行表有数据所以 QA 正常——**MVP 项目 QA 表现的隐藏变量是行表，不是构建质量**。修复三件：
1. 脚本 H 段类节点循环加 `_seen_cls_node` 去重（根治以后所有轮次）；
2. 327 存量：graph_data 去重 + `graph_rows.sync_project_rows` 手动回填（1237 实体/3390 关系）——**MVP 脚本直写 DB 绕过平台 commit 监听器是行表缺失的结构性原因**，平台化时 H 段必须显式调 sync_project_rows；
3. TBox 索引重建（39 锚点）。

**平台检索侧增强（通用，无业务词）**：`_class_inventory_sources` 尾部新增**全图类分布概览**引用（实例数 top12 类，score 0.72 让位锚定清单 0.95）——类层次边缺失场景下兄弟类展开的通用替代：计数类问题无论锚到哪个类，LLM 都能看到全图类分布自行挑类报数。QA 提示词同步加计数纪律（第 5 条：相近类一并报出并说明口径）。

**复测**（glm-5-3 QA 行）：接口 182 ✅ / XML标签 93 ✅ / 接口字段→"字段名 147、接口 182、输入项 554"多类报数+口径说明 ✅（对比修复前"8 个 Sheet"）。

**第三轮（回答体验改造，2026-11-16 深夜）**：用户反馈"不像回答、像检索摘要"。四处调整：
1. **QA prompt 重构**（retrieval.py `_QA_SYSTEM_PROMPT`）：结论先行（禁止"根据提供的上下文信息"开头）+ 推理过程要求（口径构成拆解，如"182=基线 152+梳理 30"）+ 无据时指出最接近信息而非空泛拒答；
2. **类清单引用带来源文档分布**：join provenance 按 doc 分组（"来源：基线.xls×152、梳理.xlsx×30"）——**provenance 缺失（MVP 直落项目）优雅降级**；平台管线项目自动生效；

5. **QA 模型切 glm-5-3**（model_config_id=12）：qwen3.5:9b 弃用为问答行。
